## Overview

The TUI gets a `crate::scan` model module (spec D1, D3), a tagged request path on the bus task (D4, D5), one `Mode::Scan` with four tabs (D2, D11), the cadence of D6, launch and confirm of D7, origins of D8, errors of D9, parsing of D10, the legacy `scan.discover` path kept intact (D12) and a pty cell against a real core (T7-16 to T7-20). Work proceeds in one worktree, one fresh Coder per task, strictly in the order below: dependencies first (module skeleton, bus task, `WireConfirm`), then the reducer core, then the tabs, then launch, errors and layout, then the live cell, the whole-branch tester pass and the integration task.

Inner-loop tests live in `crates/aitm-tui/tests/scan_v2_*.rs` (one file per task, named below) plus the two existing files the spec names (`scan_surface.rs`, `l4_surface.rs`) and `tester_bus_task.rs`. Every inner-loop test loads a fixture with `include_str!(concat!(env!("CARGO_MANIFEST_DIR"), "/../aitm-scan-model/fixtures/<file>"))` and adds tools with `tests/common/mod.rs` `tools(&[...])` / `connect(..)`; no task edits `CORE_TOOLS`, `bus-fixture.json` or `crates/aitm/tests/frontends.rs`. Fixture-driven tests prove the reducer, parsing and rendering only; acceptance is Task 15's pty cell (spec Acceptance criteria, "Live").

**Fan-out.** Tasks 1 and 2 touch disjoint files and could run in two worktrees (Task 1: `Cargo.toml`, `lib.rs`, `src/scan/**`, `tests/scan_v2_parse.rs`; Task 2: `action.rs`, `bus.rs`, `fixture.rs`, two stub arms in `app.rs`, `tests/tester_bus_task.rs`). Task 15 (Python) touches no Rust file and may be authored in parallel with Tasks 12 to 14, but it can only be run after Task 14. Every other task edits `app.rs` and is sequential; that is the honest answer for this surface.

**Working rules for every task.** Test first (`cargo test -p aitm-tui <name>` must fail, then pass); the full gate `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test` before the commit; commit message `feat(tui-scan): task N <name> (plan 2026-10-31-aitmproxy-scanner-v2-t7-tui)`. No new dependency beyond `aitm-scan-model` (Task 1) and, from Task 7 on, the internal `aitm-poc` crate (`aitm-poc.workspace = true`, already a transitive dependency through `aitm-scan-model`) so the TUI names the wire `aitm_poc::Severity` the issue types carry instead of mapping it through strings; Task 7 adds the dependency and retypes `IssueFilters.severity_min` to `Option<aitm_poc::Severity>` (plan amendment by the T7 session after Task 1, 2026-11-01). Parse helpers return `Option`/`Result` and never panic; no `unwrap()`/`expect()` on bus data. No em dashes in any string the operator sees. Glyphs are flat monochrome; hue only on severity and job state via `Theme::severity` and the status tokens (spec D13). Where the spec says "Left to the builder" the Coder decides and records the decision in a doc comment; where the spec is silent on behaviour the Coder stops and reports the sentence.
