### Task 6: write deadline on the line transport (TCP and stdio)

- **Satisfies:** AC14, AC15, AC16, AC21
- **Depends on:** Task 1
- **Files:** `crates/aitm-mcp/src/transport.rs` (modify; tests in its `mod tests`), `crates/aitm-mcp/Cargo.toml` (modify: add `"time"` to `tokio`'s regular `features`; the library has never used `tokio::time`)
- **Change:**
  - `async fn write_loop<W>(writer: W, sink: NotificationSink, write_timeout: Duration) -> anyhow::Result<()>` with `W: AsyncWrite + Unpin + Send`: each `write_all` and the `flush` run under `tokio::time::timeout(write_timeout, ..)`; expiry returns an error whose text starts `write timed out after`.
  - `serve_lines` reads `server.write_timeout()` once and passes it. The read half is extracted into `async fn read_loop<R>(server: Arc<McpServer>, reader: R, conn: ConnCtx, sink: NotificationSink) -> anyhow::Result<()>` so it can be raced against the writer. The writer is held as `Option<JoinHandle<anyhow::Result<()>>>` and polled by hand in a `std::future::poll_fn` (read loop first; the library's `tokio` has no `macros` feature, so no `select!`), and the `Option` is emptied the moment the handle completes, so it can never be awaited twice. `fn writer_failure(joined: Result<anyhow::Result<()>, JoinError>) -> Option<anyhow::Error>` turns a finished writer into the connection's error: the writer's own error, or a join error (a panic) with the context "the connection's writer task failed"; `None` for a clean end.
  - When the writer ends in an error before the read loop ends, the read loop is abandoned and `serve_lines` returns that error. A writer that ends cleanly, or a read loop that ends first, behaves as today. Teardown on every exit is `sink.close()` first, then `server.drop_connection(conn_id)`, then await the writer if it has not already been joined (its failure is logged at `debug`, never returned over the read loop's own outcome). Update the `serve_lines` doc.
