# Flow finish and timing design

**Status:** approved (2026-10-31, self-approved by the orchestrating session under Matt's autonomous-approve mode)
**Research inputs:** none new. The input is the review panel of PR #179 (which added `request_bytes`/`response_bytes` to `flow.get`) and a code reading of `crates/aitm-proto-http/src/{module,h2,sansio}.rs`, `crates/aitm-core/src/{flow,store,body,client}.rs`, `crates/aitm-plugins/src/{capture,detail,replay}.rs`, `crates/aitm-mcp/src/{server,json}.rs`, `apps/mac/Sources/AitmproxyKit/{FlowSummary,Flow,FlowRefetchPolicy}.swift`, `apps/web/src/{bus/types,state/app}.ts`, and `tests/e2e/web/test_bus_push_ui_contract.py`. Line numbers below were verified against `main` at `00f82ff`.

## Intent

Two gaps the PR #179 panel found. **Gap A:** an HTTP response that fails after its head is stored never becomes terminal. The head is stored with `Body::Streamed` and only the happy path (`ResponseComplete`) replaces it with a buffered body; every failure path leaves the loop with the body still `Streamed`, so `is_terminal` says no forever: `flow.clear` reports it `skipped_in_flight`, the memory-budget eviction passes it over, and `flow.get` reports `response_bytes: null` for good (which is why the macOS app bounds its re-fetch at 120 polls). **Gap B:** `flow.get` carries no timing, so the macOS flow list draws dashes in its Time and Duration columns and the connection dashboard and waterfall have nothing to plot, while `flow.table` already emits `duration_ms`. This change closes both: a failed response is finalised in the store (as a truncated, buffered body with a duration) before any error event about it is dispatched; `flow.get` gains `started_at` and `duration_ms`; the push summary becomes field-for-field the `flow.get` object and is locked to it by a test; the macOS summary decodes the two new fields into the row cells that already exist for them.

## Goals

- Every HTTP flow whose response head reached the store becomes terminal when its response ends, however it ends: completed, upstream closed early, upstream read timed out, malformed bytes from upstream, upstream I/O error, or the client went away mid-body. Terminal means `flow.clear` removes it, the memory-budget eviction can remove it, and `flow.get` reports a concrete `response_bytes`.
- A failed response is stored as the bytes captured so far (`Body::Bytes`, or `Body::Empty` when none), with `metadata.truncated == true` and `metadata.duration` set.
- The store is final **before** `Event::Error` is dispatched for that flow, so a push built from the store on that event (the MCP server pushes a flow summary on `Error`) and a web client that refetches on it both see the finished flow.
- Nothing on the wire changes: what the client receives on every path is byte-for-byte what it receives today.
- `flow.get` reports `started_at` (ms since the Unix epoch) and `duration_ms` for both flow kinds, computed by the same helpers `flow.table` uses, so the two commands never disagree.
- The `notifications/aitm/flow` push summary equals the `flow.get` object for the same flow, for both kinds, and a test fails if either side drifts.
- The macOS `FlowSummary` decodes `started_at` and `duration_ms` into `FlowRow.startedAt` and `FlowRow.duration`.

## Non-goals

- A flow whose upstream never answered at all (`response: None`) stays non-terminal. That includes the h1 "malformed response in the same read as the head" case: `Http1Machine::on_server_bytes` returns `Err` and drops the events it had parsed in that read (`sansio.rs:611-613`, the `?` on `step_chunked`), so `ResponseHeaders` never reaches the driver and no head is stored. Follow-up F1 below.
- No new `Event::Error` for a path that emits none today (upstream read timeout, upstream I/O error, client write failure). The event behaviour of every path is preserved exactly (D4).
- No new field on `FlowMeta`, `HttpResponse`, or the session/HAR formats. `truncated` is reused with a widened meaning (D2); `aitm-plugin-sessionio` copies it as a bool (`native.rs:355,367`) and needs no change.
- No change to `is_terminal` (`store.rs:229-240`); it is proven through behaviour.
- No change to the web UI's code: a push stays a trigger (web-ui-bus-push spec D3). Only comments change.
- No change to the TUI (it polls `flow.get` and never reads pushes; it does not render the new fields in this change).
- No change to `FlowRefetchPolicy`'s behaviour; its doc comment is corrected, the 120-poll bound stays as a safety net for an older core.
- `aitm-mcp` does not grow a production dependency on `aitm-plugins`.
- WebSocket flows get `started_at` but no `duration_ms` value (no end marker exists on `WsFlow`; it is `null`).

## Anti-goals

- An `Event::Error` dispatched while the store still holds a `Streamed` body for that flow.
- An `Event::Response` dispatched for an abandoned response (the malformed-trailer test's contract, `module.rs:5261`, must keep holding).
- Two timing rules: `flow.get` and `flow.table` computing `duration_ms` differently, or `started_at` for HTTP and WebSocket flows measured from different clocks.
- A hand-written push mirror that drifts from `flow.get` unnoticed.
- Losing PR #179's contract: `response_bytes` is `null` while a body is still streaming and concrete once it is not.
- Any change to the bytes a client receives, or to which failures end a connection.

## Design

**D1. One finalisation rule, in the core, next to the invariant it serves.** `aitm-core` gains two things. (a) `impl HttpFlow { pub fn abandon_response(&mut self, captured: Vec<u8>) -> bool }` in `flow.rs`: if `self.response` is `Some` and its body is `Body::Streamed(_)`, the body becomes `Body::Bytes(captured)` (or `Body::Empty` when `captured` is empty), `metadata.truncated = true`, `metadata.duration = metadata.created.elapsed().ok()`, and it returns `true`; in every other case it returns `false` and changes nothing (no response yet; a body a plugin already replaced with `Bytes`; a completed `Bytes`/`Empty` body). Idempotent by construction. (b) A **provided** method on the `FlowStore` trait in `store.rs`, `fn abandon_response(&self, id: FlowId, captured: Vec<u8>) -> bool`, implemented once in the trait body in terms of `update`: it calls `HttpFlow::abandon_response` on the stored flow when it is `Flow::Http` and returns that result, or `false` when the id is unknown or the flow is a WebSocket. No implementer changes. **(Architect's call, departing from the brief's `pub(crate)` helper in `module.rs`.)** Reasons: the rule "a response that ends early is a truncated, finished response" is the store's terminality invariant (`is_terminal`) seen from the other side and belongs in the crate that owns it; both protocol modules call one method with one shape (`ctx.store().abandon_response(id, bytes)`), through the `&dyn FlowStore` they already hold (`protocol.rs:175`); and the h1 and h2 tasks then depend only on the core task, not on each other, so they fan out in parallel. The doc comment of `is_terminal` (`store.rs:221-228`) gains one sentence: an abandoned response (buffered by `abandon_response`) is terminal like a completed one.

**D2. `truncated` widens, no new field.** The doc comment on `FlowMeta.truncated` becomes: the stored copy of a body is incomplete, either because the body exceeded the configured cap or because the response ended early (upstream closed, read timed out, malformed bytes, or the client went away); in the cap case the client still received the full stream, in the early-end case it received what the proxy had forwarded. `flow.detail`'s `body_truncated`/`meta.truncated` need no code change; their meaning follows the field's. The session/HAR formats copy the bool unchanged.

**D3. h1: one funnel for every exit of the response loop.** In `serve`, the `while !done { .. }` response loop (`module.rs:878-1016`) is wrapped so that every `?` and `bail!` inside it lands in one place after the loop: an immediately-awaited `async { .. ; Ok::<(), anyhow::Error>(()) }` block (or a local async fn; the builder chooses, D3 is about the observable contract). Inside the block, the two places that emit a fixed-words `Event::Error` today (malformed, `895-901`; upstream close, `1007-1013`) stop emitting and instead record the words in a local `fault: Option<&'static str>` before returning the error. After the block: on `Ok` nothing changes; on `Err(e)`, first `ctx.store().abandon_response(id, std::mem::take(&mut captured))`, then, if `fault` is `Some(words)`, `ctx.emit(Event::Error { flow: id, kind: FlowError::Upstream(words.to_string()) }).await`, then `return Err(e)`. The order **store, then event** is the contract (Goals, third bullet). `captured` is the same bounded buffer the success path stores, so an abandoned body never exceeds `max_body`. No `Event::Response` is ever emitted for an abandoned response. The `ResponseHeaders without a parsed response` bail (`910`) happens before any head is stored, so `abandon_response` returns `false` there, harmlessly.

**D4. Per-path event behaviour is preserved exactly.** This table is the contract the h1 tests pin; the rightmost column is new, the rest is today's behaviour.

| h1 exit path | `serve` result | `Event::Error` emitted | Store after (new) |
|---|---|---|---|
| upstream closes before the response is complete | `Err("upstream closed before completing the response")` | one, `Upstream("upstream closed before completing the response")` | body buffered, `truncated`, `duration` set |
| upstream read timed out (`READ_TIMEOUT`) | `Err("upstream read timed out")` | none | same |
| malformed bytes from upstream after the head was stored | `Err(machine error)` | one, `Upstream("malformed response from upstream")` | same |
| upstream I/O error (`r?`) | `Err(io)` | none | same |
| client write failure (`flush` `?`) | `Err(io)` | none | same |

h2 (D5) has one row: any `drive_stream` error after the head is staged yields `Err`, one `Event::Error { Upstream(e.to_string()) }` from `stream_task`, and the same store state. Making the no-event paths emit an error is a reasonable follow-up (F2) but not this change.

**D5. h2: the same funnel around the forward branch.** In `drive_stream`'s `if forward_chunks { .. }` branch (`h2.rs:545-569`), everything from `respond.send_response(client_resp, false)` through the body loop and `client_send.send_data(Bytes::new(), true)` runs inside an immediately-awaited fallible block that owns `captured`/`truncated`; on `Ok` the existing `finish_response(ctx, id, captured, truncated).await` runs; on `Err(e)`, `ctx.store().abandon_response(id, captured)` runs and `e` is returned. `stream_task`'s existing `Event::Error` emission then follows the store update, giving the same store-then-event order as h1 with no change to `stream_task`. The replaced-body branch is left alone (its stored body is already `Bytes`). A `wire(..)` timeout, an upstream reset (`chunk.context(..)`), a client-side send failure and a `send_response` failure all take the same funnel.

**D6. `is_terminal` is unchanged and proven by behaviour.** The tests assert `store.clear()` outcomes (`cleared == 1`, previously `skipped_in_flight == 1`) rather than calling `is_terminal`.

**D7. `flow.get` timing fields.** `summarize` (`capture.rs:180-220`) emits two new fields for **both** kinds: `started_at` (`TypeDesc::Int`, optional, "When the flow started, in milliseconds since the Unix epoch: the moment the proxy created the flow (the request head for HTTP, the upgrade for WebSocket); null if the clock is before the epoch") and `duration_ms` (`TypeDesc::Int`, optional, "Flow duration in whole milliseconds, from start to the end of the response, or to the point a failed response was abandoned; null while in flight or unknown"). `started_at` is `metadata.created` for both kinds **(Architect's call; the brief proposed `request.timestamp` for HTTP)**, because `duration` is measured from `created` so `started_at + duration_ms` is exactly the end time (what a waterfall needs), because a replayed flow's `request.timestamp` is the original flow's time (Constraints, "Timing sources") and would place a replay row at the wrong time, and because one rule for both kinds is one less thing to document; for a live h1/h2 flow the two clocks differ by microseconds. Two private helpers in `capture.rs`, `fn epoch_ms(t: SystemTime) -> Value` (`Int` of `duration_since(UNIX_EPOCH)` in ms, saturated to `i64::MAX`; `Null` on `Err`) and `fn duration_ms(d: Option<Duration>) -> Value` (`Int` of whole ms, saturated; `Null` on `None`), are used by both `summarize` and `flow_row` (`306-350`), replacing the inline `as_millis().min(..)` expression at `323-328`, so the two commands cannot drift. `summary_fields` (`108-166`) declares both as optional `Int`. The `flow.table` schema and values are unchanged.

**D8. The push summary is `flow.get`, field for field.** `flow_summary` (`server.rs:2631-2648`) is rewritten to emit, for `Flow::Http`: `id, kind:"http", intercept, is_replay, method, scheme, authority, path, status, request_bytes, response_bytes, started_at, duration_ms`; for `Flow::WebSocket`: `id, kind:"websocket", intercept, is_replay, handshake, messages, started_at, duration_ms`; with the same null rules as `summarize` (a `Streamed` body is `null`; no response is `null` status and `null` `response_bytes`). It stays a hand-written mirror (no production dependency on `aitm-plugins`), **locked by a test** in `crates/aitm-mcp/tests/mcp.rs` that stores one fully-populated HTTP flow and one WebSocket flow, obtains `flow.get` for each through a `Registry` carrying the real `CapturePlugin`, converts with `aitm_mcp::json::to_json`, and asserts the pushed `params.summary` is `==` to it; any drift on either side fails. `kind` changes from `"ws"` to `"websocket"`. That is safe: the web UI ignores the summary on a real bus and already maps only `"websocket"` (`app.ts:943-944, 998`); the TUI never reads pushes; the e2e tests read `authority`/`path` only, and the one that pins the key set is updated in this change (D9). `replay_since` inherits the new shape for free.

**D9. Consumers updated, behaviour untouched.** (a) `tests/e2e/web/test_bus_push_ui_contract.py`: `SUMMARY_KEYS` becomes `{"id","kind","intercept","is_replay","method","scheme","authority","path","status","request_bytes","response_bytes","started_at","duration_ms"}`; the "exactly the keys" and `kind == "http"` checks stay; the docstring lines 15-16 describe the new shape. (b) `apps/web/src/bus/types.ts:97-103` and `apps/web/src/state/app.ts:322-326`: the comments now say the server's summary is the full `flow.get` object (same keys, `kind:"websocket"`), and that the UI still treats a push as a trigger and refetches by id (a deliberate choice, not a workaround for sparseness). (c) `apps/web/src/state/app.push.test.ts` line 13 and the line-63 comment: the fixture stays as it is (a sparse, old-shaped summary is exactly what an older core sends, and the test proves it is never written), but the comment says so instead of calling it "what the server really sends". No `.ts` code changes; the web unit tests are not affected. (d) `docs/design/operator-ui-foundation.md:389`: the `flow.get` row lists `started_at?` and `duration_ms?` and its note becomes "No headers, body, conn or metadata → F5" (timing is no longer missing).

**D10. macOS.** `FlowSummary` gains `public var startedAt: Date?` and `public var duration: Duration?`, with matching `init` parameters defaulting to `nil`. `init?(json:)` decodes `started_at` as `Date(timeIntervalSince1970: Double(ms) / 1000)` when `json["started_at"]?.intValue` is a non-negative integer, else `nil` (absent, `null`, negative, or non-integral); `duration_ms` as `.milliseconds(ms)` when a non-negative integer, else `nil`. `row(seq:coreID:)` passes both to `FlowRow`. Nothing else in the app changes: the columns, dashboard and waterfall already read those two row fields, `awaitsBodySize` and `FlowRefetchPolicy` are untouched, and `FlowRow.==` needs no change (Constraints, "macOS"). The `FlowRefetchPolicy.swift` doc comment (lines 11-15) is corrected: a core with this change finalises an abandoned response (so the size lands); the bound remains for an older core.

**D11. Docs in code.** The `serve` doc comment (`module.rs:510-543`) and the `h2.rs` module doc (which already says "A failed stream emits `Event::Error` before ...", line 26) each gain one sentence: a response that ends early is stored as a truncated, finished response before the error about it is dispatched.

## Acceptance criteria

1. AC1: `HttpFlow::abandon_response(vec![1,2,3])` on a flow whose response body is `Body::Streamed` returns `true` and leaves `response.body == Body::Bytes(vec![1,2,3])`, `metadata.truncated == true`, `metadata.duration.is_some()`; with an empty vector the body is `Body::Empty`. On a flow whose response body is `Body::Bytes(..)` it returns `false` and `truncated` stays `false`; on a flow with `response: None` it returns `false`.
2. AC2: A stored HTTP flow with a `Streamed` response body is kept by `store.clear()` (`cleared == 0`, `skipped_in_flight == 1`); after `store.abandon_response(id, vec![1,2,3])` returns `true`, `store.clear()` reports `cleared == 1` and `store.get(id)` is `None`. `store.abandon_response` on an unknown id returns `false`.
3. AC3 (h1, upstream closes mid-body): an origin writes `HTTP/1.1 200 OK\r\nContent-Length: 10\r\n\r\nabc` and closes. `serve` returns `Err` whose text contains "upstream closed before completing the response"; the stored flow has `response.body == Body::Bytes(b"abc".to_vec())`, `metadata.truncated == true`, `metadata.duration.is_some()`; `ctx.store().clear()` reports `cleared == 1, skipped_in_flight == 0`; the recorded events contain exactly one `Event::Error { kind: Upstream("upstream closed before completing the response") }` for the flow and no `Event::Response` for it.
4. AC4 (h1, store before event): in the AC3 scenario, a sink that reads the stored flow when `Event::Error` is dispatched sees `response.body` already `Body::Bytes(b"abc")` and `metadata.truncated == true` at that moment.
5. AC5 (h1, upstream read timeout): under `#[tokio::test(start_paused = true)]`, an origin writes the AC3 head and `abc` and then stays silent without closing. `serve` returns `Err` whose text contains "upstream read timed out"; the stored flow is as in AC3 (`Bytes(b"abc")`, `truncated`, `duration.is_some()`, `clear().cleared == 1`); the recorded events contain **no** `Event::Error` and no `Event::Response` for the flow. The test completes in well under a second of wall time.
6. AC6 (h1, malformed after the head): the existing `serve_reports_a_malformed_trailer_section_as_one_typed_error` keeps all its assertions and additionally asserts, for the "head, then section" delivery, `response.body == Body::Bytes(b"hello".to_vec())`, `metadata.truncated == true`, and `ctx.store().clear().cleared == 1`; and, for the "head and section together" delivery, `response.is_none()` and `clear().skipped_in_flight == 1` (the documented limitation, Non-goals, pinned so a later fix flips it knowingly).
7. AC7 (h1, client goes away mid-body): an origin writes the AC3 head and `abc`, waits until told, then writes `def` and holds the connection; the client reads the head and `abc`, drops its end, and then tells the origin. `serve` returns `Err`; the stored flow has `response.body == Body::Bytes(b"abcdef".to_vec())` (captured before the failed forward), `metadata.truncated == true`, `clear().cleared == 1`; the recorded events contain no `Event::Error` and no `Event::Response` for the flow.
8. AC8 (h2, upstream drops mid-body): against a real `Proxy` with the HTTP module, an h2 origin that sends a 200 head, one DATA frame `abc`, drives its connection long enough for the frame to be on the wire, then drops the connection: the client's `h2_try_get` returns `Err`; within 5 s the stored flow has `response.body == Body::Bytes(b"abc".to_vec())` and `metadata.truncated == true`; `store.clear()` reports `cleared == 1`; an `Event::Error` for that flow id was dispatched (the existing `ErrorRecorder` plugin).
9. AC9: `flow.get` on an HTTP flow with `metadata.created == UNIX_EPOCH + 1_761_908_698_120 ms` and `metadata.duration == Some(412 ms)` reports `started_at == Value::Int(1_761_908_698_120)` and `duration_ms == Value::Int(412)`; on a flow with `duration: None` it reports `duration_ms == Value::Null`; on a WebSocket flow with the same `created` it reports `started_at == Value::Int(1_761_908_698_120)` and `duration_ms == Value::Null`. A flow whose `created` is before `UNIX_EPOCH` reports `started_at == Value::Null`.
10. AC10: the `flow.get` schema declares `started_at` and `duration_ms` as optional `TypeDesc::Int` with descriptions containing "milliseconds"; `flow.table` for the AC9 HTTP flow still reports `duration_ms == Value::Int(412)` (shared helper; `flow_table_rows` keeps passing).
11. AC11: `flow.get` on a stored HTTP flow whose `Streamed` response was finalised by `store.abandon_response(id, vec![1,2,3])` reports `response_bytes == Value::Int(3)`, `duration_ms` not `Null`, and `status == Value::Int(200)`.
12. AC12: for a stored HTTP flow with a 200 response, `Body::Bytes` request and response bodies, a set `duration`, and an explicit `created`, and for a stored WebSocket flow, the `params.summary` of the `notifications/aitm/flow` line pushed by `push_flow_event` is `==` (as `serde_json::Value`) to `to_json(flow.get result)` obtained from the real `CapturePlugin` through a `Registry`.
