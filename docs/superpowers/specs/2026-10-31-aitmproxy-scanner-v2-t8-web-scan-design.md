## Intent

Give the web operator UI the full Scan surface of umbrella D10 (Profiles, Jobs, Site map, Issues) over the D3 verb family, with scan state held in the app store so a running job survives navigation, push lines treated as refresh triggers with `scan.status`/`scan.issues` as truth, the existing confirm-over-the-wire handshake for L4/intrusive launches, and the shipped v1 `scan.discover` panel kept intact for a core that offers only the legacy verb. Proof is a real `aitm web` on a real core against `aitm-testtarget` in headless Chrome, never a fixture.

## Goals

- A core that offers `scan.start` shows the v2 Scan panel; one that offers only `scan.discover` shows the shipped v1 panel unchanged; one that offers neither shows an honest "engine not available" state.
- Start a `standard` job from the Profiles editor; watch probes/points/issues counters and the phase move in the Jobs view at <= 1 s latency from the core's truth; cancel it and see `cancelling` then `cancelled` (UI-1).
- Issues grouped by severity appear while the job runs; detail shows evidence, opens probe/baseline flows in the inspector and the PoC in Findings; `false_positive` round-trips through `scan.issue.update` (UI-2).
- An L4 or `intrusive` launch shows the core's prompt verbatim and re-issues with `_confirm`; with no L4 scope entry covering the target the launch is disabled with the D11 hint (UI-3).
- Site map and insertion points render from a real `scan.sitemap` with cursor paging (UI-5).
- Navigating to the inspector and back loses nothing: jobs, selection, drafts, filters, loaded pages.

## Non-goals

- `scan.passive` / `scan.report` views; exporting issues; a palette group for scan (the palette already lists every `scan.*` tool from `tools/list`).
- Pause/resume (umbrella non-goal); editing hard ceilings (D11: config only); authoring checks.
- Any change outside `apps/web/**` (D12 row T8). The e2e cell `tests/e2e/scan/test_t8_web_live.py` is **T10's file**; T8 ships the Node live-proof script it wraps (Verification).
- Removing or hiding `scan.discover` from the generic palette; the v1 panel files are not edited.

## Anti-goals

- Reconstructing job state from push lines; a counter that steps backwards; `done` without a terminal state; a UI-fabricated confirmation or a UI path to `scan.start` that skips the dialog when the core asked for one.
- Any cell showing a cookie/token value: the UI renders engine-redacted `example`/`matched` verbatim and never reconstructs values (D2, D7, T2-6).
- Hard-coded colours, hue on chrome, a new npm dependency, an icon outside `components/Icon.tsx`'s lucide set.
- A fixture or mock run presented as evidence (umbrella Verification).

## Constraints

- SolidJS + TypeScript, CSS modules, design tokens only (`--color-severity-<level>-fg/bg` for severity; `--color-state-<success|warning|danger|neutral>-*` for job state and pass/fail; text/ground/line tokens for everything else). Flat monochrome lucide icons via `Icon` (12 px inline, 16 px in bars); editorial typography-forward restraint; dense rows where density earns it (Jobs, Site map, Issues lists), spacious in the editor and the issue detail. Interaction rules of foundation §2.8 (hover never moves selection; keyboard actions never animate; empty states keep the frame; zero prints as zero, missing as a grey dash).
- Parsing is defensive (the v1 `parseScanResult` style): every parser returns `null` or a bounded, typed value and never throws in a component; lists are capped at the verb's own limit (issues/sitemap `limit` <= 1024, D3).
- `vitest` (`npm test` in `apps/web`) and `npm run typecheck` are the inner loop; the Rust gate is unaffected (no Rust files change). The bus is reached only through `app.call`/`app.bus`; no new WebSocket.
- Role: the UI never decides policy. On `app.bus.role() === 'agent'` the launch controls stay enabled and a note explains that the core refuses active scans without `scanner.allow_agent_active`; the refusal, when it comes, is rendered from the error code.

## Design

### D-T8.1 Where the surface lives and how it is gated

- `apps/web/src/panels/ScanPanel.tsx` becomes a three-way switch on `app.proxy.tools`: `scan.start` present -> `<Scanner/>` (new, `apps/web/src/panels/scanner/`); else `scan.discover` present -> the shipped `<Scan/>` from `apps/web/src/panels/scan/` **unchanged**; else an "engine not available" block ("The scanner is not offered by this core."). The `Panel` union and `SidebarItem` keep their existing `'scan'` member; no new panel id.
- `Sidebar.tsx`: the Scan item's gate becomes `scan.start || scan.discover`; its count is the scan store's live-job count (`"1 live"`, `null` when zero or unknown) **(Architect's call)**. Building the store from the Sidebar is what makes it exist before the panel is ever opened (the `scriptsStore` precedent, `Sidebar.tsx:55`).
- The v2 surface never offers `scan.discover`; `scan.map` is the mapping action (D3, umbrella call 18).

### D-T8.2 Information architecture **(Architect's call)**

Inside the lower region the panel is: a header row (title "Scan" with the `search` icon; a `role="tablist"` segmented strip **Profiles · Jobs · Site map · Issues**, each tab with its count: profiles n, live/total jobs, nodes, issues total), then a persistent **job strip** for the selected job (one dense line: `StatusDot` by state + state/phase words, `probes sent/budget`, `points audited/found`, a severity stacked bar, elapsed, and a `Cancel` button; hidden when no job exists), then the active view. Every view is the Findings list+detail grid (320 px list, detail right; `@container (max-width: 900px)` stacks list over detail, as `findings.module.css:679`); at `@container (max-width: 600px)` the job strip wraps to two lines, list rows hide their secondary column (confidence/lane on issues, host on nodes, elapsed on jobs) and the tab strip scrolls horizontally. Tabs: ArrowLeft/ArrowRight move between tabs; each list is a `role="listbox"` with ArrowUp/Down/Home/End and Enter focusing the detail, exactly as `Findings.tsx:46-72`.

**Selected job** (`store.selectedJob`) scopes the job strip, Site map and Issues. Default: the newest job. Selecting a Jobs row changes it; starting a job selects the new one and switches to the Jobs tab. Issues has an "All jobs" toggle (job filter cleared) **(Architect's call)**.

### D-T8.3 Scan store (state outlives the panel)

`apps/web/src/panels/scanner/store.ts`: `scanStore(app: AppStore): ScanStore` on the `WeakMap<AppStore, …>` + `createRoot` pattern of `findings/state.ts`. Signals: `offered: Accessor<'v2' | 'legacy' | 'none'>`, `jobs: Accessor<JobSummary[]>` (newest first, from `scan.list`), `status: (job: string) => JobStatus | null`, `selectedJob`/`setSelectedJob`, `liveCount: Accessor<number | null>`, `profiles: Accessor<ProfileListEntry[]>`, `drafts: Map<string, ProfileDraft>` (editor drafts per profile name with `dirty`), `checks: Accessor<CheckMeta[]>`, `sitemap: (job) => SitemapPage` (`nodes`, `points`, `nextCursor`, `loading`, `error`), `issues: (job | null) => IssuesPage` (`rows: IssueSummary[]`, `bySeverity`, `nextCursor`, `loading`, `error`), `issueDetail: (id) => Issue | null`, `tab`/`setTab`, per-view selection ids and filters, `busy`, `lastError: Accessor<ScanError | null>` where `ScanError = { source: 'launch' | 'save' | 'delete' | 'preview' | 'cancel' | 'issue' | 'profile'; code: ScanErrorCode | null; text: string }` (typed so that each view renders only the sources it owns: the editor `launch`/`save`/`delete`/`preview`, the profile-load block `profile`, Jobs `cancel`; amendment A8), `statusError: (job: string) => string | null` (a failed per-job `scan.status` read; amendment A8). Actions: `refreshJobs()`, `refreshStatus(job)`, `refreshIssues(job)`, `loadMoreIssues(job)`, `refreshSitemap(job)`, `loadMoreSitemap(job)`, `loadProfiles()`, `loadProfile(name)`, `saveProfile(draft)`, `deleteProfile(name)`, `loadChecks()`, `loadL4Scope()`, the memoised `ensureProfiles()`, `ensureChecks()`, `ensureL4Scope()`, `ensureJobs()` (each issues its first read once and returns the same promise afterwards, so the shell and the views never issue duplicate bootstrap reads; amendment A8), `previewSession(origin)`, `launch(profile, mode: 'start' | 'map'): Promise<LaunchOutcome>`, `confirmLaunch(token): Promise<LaunchOutcome>`, `cancel(job): Promise<CancelResult>` (`{ ok: true; status: JobStatus } | { ok: false; message: string }`; a failure also sets `lastError` with `source: 'cancel'`), `updateIssue(id, status, note?)`. Every bus call goes through `app.call`; failures land in the view's own error block (foundation §2.8), row actions also toast via `app.notice`.

**Live update model** (D3 "push is a trigger, poll is truth"; the flow store's rule at `app.ts:498-520`):

- On creation the store registers `app.bus.onNotification` and handles `notifications/aitm/job` with `kind === 'scan'` (parsed by `parseJobNotification`; anything else ignored). A line is only a trigger: it schedules `refreshStatus(job)` (coalesced to at most one in-flight read per job per **250 ms**), on `started` also `refreshJobs()`, on `issue` also `refreshIssues(job)` (coalesced **500 ms**), on `finished|cancelled|failed` both plus a final `refreshIssues`. The line's `status` summary and `issue` payload are **never written into the store**. A line whose `seq` is <= the last seen `seq` for that job is dropped.
- **Poll**: while any job is non-terminal (`queued|running|cancelling`), `refreshStatus` for each such job every **1000 ms** and `refreshJobs` every **5000 ms** (jobs started by the TUI, mac or the agent appear without a push), regardless of which panel is mounted **(Architect's call**: 1 Hz is at or under the 4/s push coalescing and keeps a 2-job poll at two small reads per second). While the Issues view is mounted and its job is live, `refreshIssues` every **5000 ms** as a heartbeat. Polling stops when every job is terminal. Only an `open` bus is polled; on a bus transition to `open` after `reconnecting`, the store re-reads `scan.list` and every job's status (the flow store's "every (re)connection is a new stream" rule, `app.ts:721`).
- **Monotonic**: `isStale(held: JobStatus, incoming: JobStatus): boolean` = `incoming.elapsed_ms < held.elapsed_ms && !isTerminal(incoming.state)`; a stale reply is ignored whole. A terminal reply is always accepted. Counters therefore never step backwards in the UI (D5: counters are monotonic).

### D-T8.4 Model and parsers (`apps/web/src/panels/scanner/model.ts`)

TypeScript mirrors of the D2/D5/D6/D7 wire types with the enum tokens as string-literal unions (`JobState`, `Phase`, `StoppedReason`, `Lane`, `Intensity`, `Speed`, `Accuracy`, `InsertionKind`, `PointTrait`, `Confidence`, `IssueStatus`, `Technique`, `CheckCost`, `CheckOrigin`). Parsers, each `(raw: unknown) => T | null`, defensive, tested against **every fixture file** in `crates/aitm-scan-model/fixtures/` (read by the vitest suite from the repo path; shapes only, never acceptance): `parseJobStatus`, `parseJobSummary`, `parseStartResult`, `parseListResult`, `parseIssuesResult`, `parseIssue`, `parseIssueSummary`, `parseSitemapResult`, `parseInsertionPoint`, `parseChecksResult`, `parseProfileList`, `parseScanProfile` (unknown keys dropped; a missing block takes the Rust `Default` impls of `crates/aitm-scan-model/src/profile.rs`, e.g. `lanes: ['http']`, never the `standard` fixture, amendment A4), `parseSessionProfile`, `parseJobNotification`. Additive engine fields (PR #232, amendment A5): `CrawlCounters.errors` and `CrawlCounters.forms_skipped` (`number`, absent -> `0`), `Issue.jobs` and `IssueSummary.jobs` (`string[]`: every job that found or re-found the issue; `job` stays the first finder; absent -> `[]`). `parseScanError(message: string): { code: ScanErrorCode | null; detail: string }` mirrors `ScanErrorCode::parse_message` (`scan: <code>: <detail>`; unknown code -> `null` with the raw text). Pure helpers: `isTerminal(state)`, `isStale`, `fmtElapsed(ms)` (`0:42`, `12:03`, `1:02:03`), `groupBySeverity(rows)`, `filterIssues(rows, f)`, `nodesByHost(nodes)`, `hostInScope(origin, scope)` (exact host, `host:port`, or `*.wildcard` suffix match, the v1 LaunchForm rule), `l4EntryCovers(entry: L4ScopeEntryWire, ip, port)` (IPv4 CIDR + port range + `capability === 'inject'` + `direction === 'outbound'` + interface `*`/`any`/empty via `scopeCoversInterface`; an IPv6 or unparsable `cidr` returns `null` = unknown), `applyCheckToggle(sel: CheckSelection, target: { id } | { class } | { lane }, on: boolean, checks: readonly CheckMeta[]): CheckSelection` (the catalogue is the fourth argument because an id does not encode its class, amendment A4), `checkIsOn(sel, meta)`, `isValidProfileName(name): boolean` with `PROFILE_NAME_HINT` (D-T8.5, amendment A1) (on when `include` is empty or matches `id`/`class`/`<lane>:*`, and `exclude` does not match).

### D-T8.5 Profiles view and editor

- List (left): from `scan.profile.list`, built-ins first with a `builtin` tag, then saved; a dirty draft shows a dot. Selecting loads `scan.profile.get { name }` into a draft unless a draft exists. Default selection `standard`.
- Editor (right), sections in this order, bound to `ScanProfile` (D2) field for field: **Name** (read-only for a builtin; "Save as" needs a new name). A saved-profile name must match the engine's rule `^[a-z0-9][a-z0-9._-]{0,63}$` (lowercase only; a built-in name is refused; `crates/aitm-plugin-scanner/src/profiles.rs:37` on PR #232): for a non-conforming or built-in name the editor disables `Save` and shows the hint `lowercase letters, digits, . _ - ; 1-64 characters, starting with a letter or digit`; when the engine still answers `invalid_profile` its text is rendered verbatim (amendment A1). **Targets**: origins list with an "Add origin" picker: a segmented `role="radiogroup" aria-label="Origin scheme"` (`https` default, `http`; not a `<select>`, because headless Chrome cannot drive a native select with real input events, amendment A2), an in-scope concrete host from `app.proxy.scope` (no `*.` entries) in a `<select aria-label="Origin host">`, and an `Origin port` input that is disabled when the chosen host already carries a port, in which case the origin is `scheme://host`; plus the `AddHost` widen-scope affordance from `panels/scope/AddHost`; an origin not in scope is flagged "not in scope" with an inline "Add <host> to Scope". L4 targets rows (`ip`, `port`, `proto`, `grammar?`; inputs labelled `L4 target IP`, `L4 target port`, `L4 target proto`, `L4 target grammar`, button `Add L4 target`) with the D11 hint printed verbatim under the list: "The L4 stream lane needs an L4 scope entry with `interface: "*"`, `direction: outbound`, the target CIDR and port range, and the `Inject` capability." **Lanes** toggles (`http`, `ws`, `l4_packet`, `l4_stream`); a lane absent from `scan.checks` (no check lists it) is shown with "not available on this build" but stays toggleable (D1: skipped and reported, refused only when all are unavailable). **Intensity / Speed / Accuracy** segmented controls; `intrusive` carries the note "operator only; asks for confirmation". **Checks**: tree from `scan.checks` grouped lane -> class -> check (`name`, `id`, cost, technique, typical severity pill, origin badge native/bundled/custom); class rows are tri-state checkboxes, check rows checkboxes, both written through `applyCheckToggle` into `checks.include`/`checks.exclude` using the `id | class | lane:*` grammar; a raw include/exclude text field (one selector per line) exposes the grammar directly **(Architect's call**: the tree writes `exclude` entries unless `include` is already non-empty, in which case it edits `include`). **Crawl**, **Audit** (`kinds` multi-select, `ignore` rules as `kind?/name_regex?/trait?` rows, two numbers), **Session** (`mode`, `on_lost`, `from_flow`; a "Preview" button per origin calls `scan.session.preview { target }` and prints names only: "cookies: sid · headers: authorization" and the canary line "Canary: GET /account (expects 200)" or "Canary: none; auth-lost detection off"), **Budget**, **HTTP** (`version`, `record_probes`), **WS**, **L4** (incl. `dry_run`, `seeds`).
- Footer: `Save` (`scan.profile.save { profile }`; disabled for a builtin name), `Delete` (`scan.profile.delete { name }`, saved profiles only, inline confirm), `Map only` (`scan.map`) and the single primary `Start` (`scan.start`). Both launch verbs send **`{ profile: <the draft, whole> }`** inline **(Architect's call**: one code path, what-you-see-is-what-runs, no partial-merge semantics to get wrong, an unsaved tweak can run; `profile_name`/`target`/`overrides` are not used by the UI).

### D-T8.6 Launch flow, gating and errors

- `launch(profile, mode)` runs `beginGuarded(app.call, verb, { profile })` from `panels/l4/inject.ts`; `confirm` -> the `ConfirmInject` dialog with `title="Confirm scan"`, the core's `prompt` **verbatim**, and a new optional `confirmLabel` prop (`"Start scan"`; the dialog's default stays "Send to wire") -> `confirmGuarded(..., token)`. `done` -> `parseStartResult`; `refused` -> `parseScanError`. The UI never predicts whether a prompt will come; it only notes under the button when the draft has an L4 lane or `intensity: intrusive`: "The core will ask for confirmation."
- **Pre-flight disable** (courtesy; the core is the enforcement, as `l4/model.ts:141` says): `Start`/`Map only` are disabled with a reason line when: no origin and no L4 target; any origin fails `hostInScope` ("out of scope: add <host> to Scope"); the draft has an L4 lane and `l4.scope.list` is not offered ("the L4 layer is not enabled on this core"); the draft has an L4 lane and `l4EntryCovers` is `false` for some L4 target over the live `l4.scope.list` ("no L4 scope entry with Inject covers <ip>:<port>" + the D11 hint). An `unknown` coverage result (IPv6) does **not** disable. The bus not `open` disables everything.
- **Error rendering** (every D3 code, from `parseScanError`), shown in the editor's result block and as a toast: `out_of_scope` -> "Out of scope: <detail>" with the Add-to-Scope affordance; `refused_agent` -> `AGENT_REASON`-style text ("Agent session: the core refuses active scans unless scanner.allow_agent_active is set; intrusive is operator-only") + detail; `refused_l4` -> "L4 refused: <detail> (l4.enabled, scanner.allow_agent_l4_fuzz, l4.allow_agent_inject)"; `lane_unavailable` -> "No requested lane is available on this build: <detail>"; `busy` -> "Busy: <detail> (max_jobs or an origin already being scanned)"; `invalid_profile` -> "Invalid profile: <detail>" (the editor keeps the draft); `unknown_check` -> "Unknown check: <detail>" and the check tree highlights selectors that match nothing; `confirm_required` -> "Confirmation required" and the dialog is re-run; `not_found` -> "Not found: <detail>" (a job/issue/profile that vanished; the list is refreshed); unknown code -> the raw message verbatim.
- **After a start**: toast "scan-xxxx started", select the job, switch to Jobs; the job detail shows a dismissible notice listing `clamped` ("budget.probes: 50000 -> 20000") and `lanes.skipped` ("ws: lane not available on this build"), and `dry_run: true|false` when present.

### D-T8.7 Jobs view

List rows (dense, newest first, from `scan.list` plus the full `scan.status` where loaded), each **two lines** (amendment A3): line one the `StatusDot` with state tokens (queued/running/cancelling -> neutral, done -> success, cancelled -> neutral, failed -> danger), the words `running · auditing` and the elapsed via `fmtElapsed`; line two the job id, `probes 418/2000`, `points 80/120` and a **56 px** severity **stacked bar** (one segment per severity with `--color-severity-<level>-fg`, width proportional to `issues.by_severity`, `title` with the counts; grey when zero). A row carries no `Cancel` button. Detail: a header with the job id and the `Cancel` button, then profile name, targets, `started_by.frontend`/`client_label`, started/finished times, phase, `probes` (sent/budget/errors/timeouts/rate_waits, by lane), `crawl` (pages, forms, plus `errors` = failed browser crawls where the client crawl stood in, and `forms_skipped` = destructive-looking forms skipped; both absent -> 0, amendment A5), `points` incl. `skipped`, `checks` (scheduled/done and the `running` ids), `issues.by_severity`/`by_confidence`, `l4` counters when present, `session` (reused/lost/canary/browser_partial), `lanes` report, `clamped`, `stopped_reason` rendered as: budget -> "stopped: probe budget reached"; time -> "stopped: time budget reached"; cancelled -> "cancelled by operator"; session_lost -> "stopped: session lost"; errors -> "stopped: too many errors"; policy -> "stopped: agent policy changed"; guard_refused -> "stopped: guard refused"; failed -> "failed"; `error` text verbatim on `failed`. `Cancel` lives in the **job strip** and in the **Job detail header**, not on each row (amendment A3); it calls `scan.cancel { job }`; the row shows `cancelling` from the reply and `cancelled` from the next truth read; the button is idempotent and disabled once terminal; a `cancel` failure surfaces the core's text through the typed `lastError` (`source: 'cancel'`, D-T8.3) in the Jobs view's error rendering (amendment A8). A per-job `scan.status` read failure is shown in the Job detail as an error block with `Retry`, from `statusError(job)` (amendment A8). A finished job keeps its issues (D5).

### D-T8.8 Site map view

`scan.sitemap { job, limit: 1024, cursor? }` paged with "Load more" while `next_cursor`. A map is per job: the list header names the job id whose map is shown (the engine's `scan.sitemap {}` without a job returns the newest job's map; the UI always sends `job`, amendment A6). Left: tree grouped by `host[:port]` -> nodes (`Badge` method hue, `path_template`, `points` count, `audited` check icon, `auth` lock icon). Right: the selected node's facts and its `flows` (each a button: `openFlow(id)` = `app.select(id)`, which sets the panel to the inspector and loads the detail (`app.ts:1150`); a `null` from `loadDetail` toasts "flow <id> is not in the store"), then the insertion points whose `site_node` is the node (all points when none selected): `kind` badge, `name`, `path`, `traits` chips, `frequency`, `method`/`url`, and `example` **verbatim** (the engine redacted it; `<redacted>` prints as is). Returning from the inspector (Sidebar -> Scan) restores the tab, selection and pages from the store.

### D-T8.9 Issues view

`scan.issues { job?, limit: 1024, cursor? }` (job omitted under "All jobs"); further filtering is **client-side** over the loaded pages **(Architect's call**: instant, no refetch per keystroke): chips for confidence, lane, class (from the loaded rows), status, and a text filter over `name`/`path_template`/`name`-of-point. Rows grouped under severity headers critical -> info with group counts (hidden group when zero; the strip's bar uses the server's `by_severity`), each row: `SeverityPill` (reused from findings), `name`, `location.method path_template`, `kind:name`, confidence, lane, status tag, `occurrences` when > 1. ## Summary

The web Scan surface is a four-tab panel (Profiles, Jobs, Site map, Issues) with a persistent job strip, built on a per-app-store `scanStore` that subscribes to `notifications/aitm/job` as a trigger, polls `scan.status`/`scan.list` while any job is live regardless of what is mounted, rejects stale replies, and keeps drafts, selections and pages across navigation. Launch sends the edited profile inline through the existing `beginGuarded`/`confirmGuarded` handshake and `ConfirmInject` dialog; pre-flight disabling explains scope and L4-scope gaps with the D11 hint; every D3 error code has a defined rendering. The v1 `scan.discover` panel stays for legacy cores. Proof is `apps/web/scripts/scan-live.mjs`: a real `aitm web`, real core, real `aitm-testtarget`, real Chrome input, every rendered value cross-checked against a witness bus connection.
