# 25 — One-shot `aitm <group> <verb>` on a running core

**Stage 1 research note.** Written 2026-11-01 by the Researcher for the spec amendment that closes R14 (`docs/superpowers/specs/2026-11-01-cli-terminal-reporting-design.md`, Non-goals and Open question 1). Nothing here is a decision; options are marked *candidate*. Every file and line cite was read on 2026-11-01 in the worktree `.wt/r14` (branch `claude/cli-oneshot-live-core`, base `ddbc77bf`). Web sources were read on 2026-11-01.

## 1. Question

How should a one-shot `aitm <group> <verb>` find and talk to an already-running aitm core (the macOS app's embedded core, or a terminal `aitm` / `aitm web` / `aitm tui`) so that `aitm scope add --host x` changes the running core's Scope, and what exactly should it say when no core is running?

## 2. Short answer

A one-shot can reach a core only where the core publishes a connectable bus. The client pieces exist (`aitm-bus-client`, the TUI's token and role handling, the `-32001` refusal). The gaps are discovery and verb scope. The mac app hides its embedded core's address and fresh tokens in a per-launch temp dir passed by `--config`, so the default config dir finds nothing; default terminal `aitm` serves stdio and publishes no bus. `Sensitivity` cannot split live from local verbs, and four Cli-only gates refuse an operator-token caller.

## 3. Findings

### 3.1 How a running core publishes itself (brief item 1)

**F1. The endpoint file is written by the loopback transport, not by `main`.** `LoopbackTcp::bind(port, token, endpoint_file)` (`crates/aitm-mcp/src/transport.rs:294-310`) binds `127.0.0.1:<port>` (`0` = ephemeral), then calls `write_endpoint_file` (`:374-390`): open `write+create+truncate`, mode `0600` (applied only when the file is created, `:382`), body = `writeln!(file, "{addr}")`, i.e. exactly `127.0.0.1:50512\n`, **never the token** (unit test `endpoint_file_written_after_bind`, `:497-527`). It is **not atomic** (truncate, then write), so a reader can see an empty file; the mac app's parser returns `nil` for an empty or partial file and keeps polling (`EmbeddedCoreLaunch.swift:141-152`, `EmbeddedCore.swift:250-275`). The file is removed in `Drop for LoopbackTcp` (`:355-362`, `remove_endpoint_file` `:393-401`), which runs when the serve future is dropped: clean exit, error, and SIGINT/SIGTERM (the `select!` in `crates/aitm/src/main.rs:1094-1108` has a `shutdown_signal()` arm). It is **not** removed on SIGKILL or a crash. The doc comment warns the caller to place the file in a directory only the operator can write, because the write is not `O_NOFOLLOW` (`:366-373`). (2026-11-01)

**F2. Config surface, and the defaults that matter.**
- `McpTransport::{Stdio, LoopbackTcp{port, token, endpoint_file: Option<PathBuf>}, StreamableHttp{bind, token, allowed_origins, path}}` (`crates/aitm-core/src/config.rs:288-317`). **The default is `Stdio`** (`McpConfig::default`, `:361`).
- `mcp.operator_token` is a separate `Option<String>`: "**Off by default**: without it, every loopback connection is an agent" (`config.rs:341-345`). The loopback listener adds it with `with_operator_token` (`server.rs:1507-1516`); a token line matching it yields `Frontend::Operator`, the transport token yields `Frontend::Mcp`, anything else is refused (`transport.rs:432-448`, `classify_token`; exactly one JSON key, constant-time compare).
- `endpoint_file` has **no default**: unset writes nothing (`config.rs:293-299`, test `no_endpoint_file_writes_nothing`, `transport.rs:530-540`). YAML form: `mcp.transport.loopback_tcp.{port, token, endpoint_file?}` and `mcp.operator_token` (`crates/aitm/src/config_file.rs:549-580`, `:653-700`).
- `--bus-endpoint-file <path>` overrides `endpoint_file`; it is split off `argv` in `parse_invocation` (`main.rs:267`, `split_bus_endpoint_file_arg` `:1240-1265`) and applied by `apply_bus_endpoint_file` (`:457`, `:1271-1290`) **for every mode including `Mode::Cli`**. Over a stdio config it is an error ("`--bus-endpoint-file needs the loopback-TCP bus…`"). Its meaning today is "where the core *writes*"; reusing it for a one-shot to *read* would invert it. (2026-11-01)

**F3. Which terminal modes serve a connectable bus.** With the default (stdio) config: bare `aitm` serves MCP on stdin/stdout (`main.rs:1092`, `stdio_eof_note`); `aitm tui` logs a WARN and serves **no** agent transport (`crates/aitm/src/tui.rs:259-262`); `aitm web` serves the `/bus` WebSocket bridge on the web port plus the (stdio) primary transport. So **with no config, no terminal mode offers a second client anything to dial.** With `mcp.transport.loopback_tcp` configured, bare `aitm`, `aitm tui` (`tui.rs:250-258`, `build_servers`, agent arm with `with_mcp_roles(operator_token, …)`) and `aitm web` (`main.rs:994-1000`) all serve it. `aitm web`'s bridge tokens are not on disk: the agent bridge token is `--token` / `AITM_WEB_TOKEN` / generated per run, the operator bridge token is fresh per run and exists only when `mcp.operator_token` is non-empty (`crates/aitm/src/web/bridge.rs:489-507`, `web/mod.rs:41,141-186`, `main.rs:1029-1042`); both reach a human only through the ready card's `#t=` URL. (2026-11-01)

**F4. The macOS app's embedded core: app-chosen, per-launch, fresh tokens.** `EmbeddedCore.spawn()` (`apps/mac/Sources/Aitmproxy/Bus/EmbeddedCore.swift:151-243`):
- draws **two fresh 256-bit tokens per launch**, the agent token and the operator token (`:157-158`, `EmbeddedCoreLaunch.freshToken`, `EmbeddedCoreLaunch.swift:36-41`: "Generated once per launch, never persisted or logged");
- makes a work dir `NSTemporaryDirectory()/aitm-embedded-core/<UUID>/`, mode `0700` (`makeWorkDir`, `:358-365`), puts `config.yaml` (written `O_NOFOLLOW`, `0600`, `fchmod`, `EmbeddedCoreLaunch.swift:323-340`) and `bus.endpoint` there (`:186-188`), and spawns `aitm --config <that config.yaml>` (`:213`);
- the generated YAML is `listen: "127.0.0.1:<port>"`, `mcp.transport.loopback_tcp.{port: 0, token: <agent>, endpoint_file: <work>/bus.endpoint}`, `mcp.operator_token: <operator>`, `browser.*`, plus optional `ssl_insecure`, `macos_capture`, `scope.entries` (`EmbeddedCoreLaunch.swift:241-290`); **no `ca:` section**, so the CA is the default persistent one;
- dials the endpoint with the **operator** token (`:242-243`); removes the whole work dir on an orderly stop (`teardownChild`, `:327`: SIGTERM, then SIGKILL after a grace); a stale `bus.endpoint` is deleted before each spawn (`:189-191`).

**Observed on this Mac (metadata only; I did not read any `config.yaml`):** three work dirs coexist under `/var/folders/0t/…/T/aitm-embedded-core/` (`7D840018-…` 17:11, `C52A8B52-…` 16:58, `C8AEBDB0-…` 15:15), each `drwx------` holding `bus.endpoint` (16 bytes, `-rw-------`) and `config.yaml` (`-rw-------`). Whether the older two cores are alive is **unverified**: the sandbox denies loopback connects (`nc: connectx to 127.0.0.1 port 60680 (tcp) failed: Operation not permitted`), so "refused" in my probe was the sandbox, not the cores. The point stands without it: more than one candidate dir exists, and "pick the newest" is the trap the memory note `aitmproxy-mac-live-proof-recipe` names ("Never pick 'the newest config.yaml in the shared temp dir' to find your core: the real /Applications app (or a sibling session) spawns cores there too"). (2026-11-01)

**F5. Is that the config the CLI reads by default? No.** The CLI's default is `<dirs::config_dir()>/aitmproxy/config.yaml` (`crates/aitm/src/config_file.rs:34-36`; `~/Library/Application Support/aitmproxy/config.yaml` on macOS, `~/.config/aitmproxy/config.yaml` on Linux; `--config`, then `AITM_CONFIG`, `main.rs:56,422-428`). The embedded core never reads it (it is spawned with `--config <tmp>`), and **on this Mac that file does not exist** (`ls "$HOME/Library/Application Support/aitmproxy/"`: `audit*.jsonl`, `ca/`, `ca-audit.jsonl`, `columns.json`, `findings.json`, `logs/`, `rules.json`, `system-proxy-watchdog.log`; no `config.yaml`). The app reads the *default* config only for its **external** lane: `BusEndpoint.fromConfigFile` takes `mcp.transport.loopback_tcp.{port, token}` (`apps/mac/Sources/AitmBusClient/BusEndpoint.swift:15-43`; `BusService.configURL` honours `AITM_CONFIG`, `BusService.swift:402-407`), and note it reads the **agent** token; the operator token has to be pasted (`BusEndpointSettings.endpoint`, `BusEndpointSettings.swift:45-59`; INSTALL.md:70-74). (2026-11-01)

**F6. Answer to "given only the operator's default config dir, can a one-shot find the embedded core's endpoint file and token?"** **No.** The path is app-chosen (UUID dir under the per-user temp dir), the tokens exist only in that dir's `config.yaml` (and the app's memory), and nothing under `~/Library/Application Support/aitmproxy/` points at them. `$TMPDIR` is not even a reliable way to reach the temp root from a CLI: in this session `TMPDIR=/tmp/claude-501` while `getconf DARWIN_USER_TEMP_DIR` is `/var/folders/0t/zkzp_fls4cx5nvx_7zhbw7580000gn/T/`. The orchestrator's design ("endpoint file plus operator token from the 0600 config") matches the embedded core's artifacts exactly (`bus.endpoint` and `config.yaml` are siblings, both `0600` in a `0700` dir) but needs a way to learn which directory; that sibling relationship is an app convention, not a contract. It does work as written for a **terminal core** whose operator wrote `endpoint_file` and `operator_token` into a config the one-shot is also pointed at (default config, `AITM_CONFIG` or `--config`). (2026-11-01)

**F7. A related hazard on the default config.** `aitm operator-token generate` rewrites the config through `write_atomically`: `std::fs::write(&tmp, data)` then `rename` (`crates/aitm/src/operator_token.rs:175-190`). By code reading (not run), the replacement is created with the process umask (typically `0644`), so a config the operator had `chmod 600` comes out wider; nothing in the file sets a mode. It also refuses when there is no config (`NoConfigFile`, `:151-160`) and tells the operator to restart: "restart the proxy … for it to take effect" (`:194-198`). So "the token in the 0600 config" is only guaranteed for the app's per-launch file. (2026-11-01)

### 3.2 The existing client precedent (brief item 2)

**F8. `aitm-bus-client` API.** (`crates/aitm-bus-client/src/lib.rs`; deps `anyhow`, `serde`, `serde_json`, `tokio`; `aitm` already depends on it via `tui.rs:35`.)
- `TcpTransport::connect(addr, token)` (`:153-181`) opens the socket, writes `{"token":"…"}\n` first, starts a reader task; the token is **not verified at connect**, a wrong token surfaces on the first request as `BusError::Rpc{code:-32001,…}` (`:154-156`; the read loop turns a `null`-id error into `Closed::Refused`, `:315-321`). `connect` failure text: `connecting to the bus at {addr}` plus the OS error (`:160`).
- `BusClient::new(Box<dyn BusTransport>)`, `initialize(client_name, client_version) -> ServerInfo{name, version, protocol_version, role: Option<String>}` (`:371-384`, `:433-462`), `tools_list()` (`:465`), `call(name, args: Value) -> Result<Value, BusError>` (`:477-510`), `ping()` (`:513`). `call` returns `structuredContent`, or the first text parsed as JSON; `isError:true` becomes `BusError::Tool(text)`; a JSON-RPC error `BusError::Rpc{code,message}`; a dead socket `BusError::Transport`; a malformed reply `BusError::Protocol` (`:44-72`, `:477-557`).
- `InProcessTransport::new(handler)` wraps an `McpServer::handle`-shaped closure on the blocking pool (`:345-367`), used by `aitm tui`.
- `read_token_file(path)` trims and refuses empty (`:572-582`).
- **There are no timeouts anywhere**: `TcpStream::connect` and `rx.await` can wait forever. A one-shot must wrap connect, `initialize` and each call in its own deadline. (2026-11-01)

**F9. The TUI is the template for a human-side client.** `crates/aitm-tui/src/main.rs:1-130`: `--bus host:port` with `--token-file p` | `--token t` ("visible in `ps`") | `AITM_BUS_TOKEN`; `AITM_BUS` as the env twin; `--expect-role agent|operator` (client-side only, "never sent to the server"); a bus off loopback is refused unless `--allow-remote-bus` (`check_bus_address`, `:40-48`, `REMOTE_BUS_REFUSED`). It learns its role from the top-level `role` field of the `initialize` result (`"operator"` | `"agent"`, `crates/aitm-mcp/src/server.rs:986-991,1611`; `BusEvent::Connected{role}`, `aitm-tui/src/bus.rs:156-170`) and maps `-32001` to a fixed refusal: "bus refused the token: it matched neither the agent nor the operator token (check the token you supplied)" (`bus.rs:30-33`, no retry). Its reconnect loop (500 ms doubling to 10 s) and its words for a dead bus are `connecting to the bus…`, `bus disconnected`, `bus down · retrying`, `not serving` (`crates/aitm-tui/src/ui/bars.rs:92-94,453-456`). The mac app's words: Core lane `external` / `not running` / `running` / `starting…` / `failed` / `stopped`; Bus lane `connected` / `connecting…` / `bus failed` / `offline` with remedies "Start the core", "Reconnect", "Paste the operator token in Settings ▸ Bus, then reconnect" (`apps/mac/Sources/AitmproxyKit/ConnectionSummary.swift:315-369`). The glossary forbids "server, daemon, backend" for Core (`docs/superpowers/specs/2026-10-31-macos-status-page-and-first-run-design.md`, §5 Words). (2026-11-01)

**F10. Result and argument encoding over the bus.** Every `tools/call` success carries `structuredContent: <json>` (`server.rs:2586-2592`, `tool_ok`), so a `Value::Str` comes back as a JSON string (no JSON-reparse ambiguity) and `Value::Bytes` as a **base64 string** (`crates/aitm-mcp/src/json.rs:14-32`, `to_json`); `from_json(j, &TypeDesc)` is the inverse and decodes `TypeDesc::Bytes` from base64 (`:62-72`). The one-shot's renderer (`crates/aitm/src/render.rs:12-18`) prints `Str` raw, `Bytes` raw, everything else pretty JSON, so a remote path that keeps today's output needs the command's **result `TypeDesc`** to rebuild a `Value` (screenshots and `ca export --format der` are `Bytes`). On the way in, the CLI parses a `Bytes` flag as the argument's UTF-8 (`crates/aitm-cli/src/dispatch.rs:308`) while the bus expects base64, so the typed `Params` must go through `to_json` rather than raw flag text. A reply with `needs_confirmation` is an ordinary `Ok(Value)` to `BusClient::call` (see F20). (2026-11-01)

**F11. What a one-shot could reuse verbatim:** `aitm-bus-client` (`TcpTransport`, `BusClient`, `BusError`, `read_token_file`), `aitm_mcp::json::{to_json, from_json}`, `check_bus_address`-style loopback refusal (the mac app does the same for the endpoint file, `EmbeddedCoreLaunch.swift:148-160`, S4), the `-32001` text, `initialize.role`, `render_cli_value`, `aitm_cli::Cli`'s flag parser (it needs a `Registry` for schemas, see F15). What is new: discovery, deadlines, the live/local split, the role check, the confirm re-send, and a `clientInfo.name` for the audit trail (`declared_client_label`, `crates/aitm-core/src/audit.rs:342-355`, rewrites names that read as the server's own, e.g. `web-bridge`). (2026-11-01)

### 3.3 Which verbs need the live core (brief item 3)

**F12. `Sensitivity` does not answer the question.** The enum is the agent policy tier, `Read | Write | Sensitive`, default `Sensitive` (`crates/aitm-core/src/command.rs:43-56,73-78`). It cuts across live-vs-local: `flow.list` is `Read` and live; `poc.build` is `Write` and needs a captured flow from the store; `scope.add` is `Sensitive` and live; `ca.install` is `Sensitive` and touches only the OS trust store; `script.validate` is `Read` and static; `findings.record` is `Write` and writes disk. (Per-command tiers extracted by reading every `impl Command` in `crates/*/src`; the test `crates/aitm/tests/m4_sensitivity.rs` pins only a subset.) The only existing machine-readable signal for "needs a serving process" is one verb's own check: `proxy.system.set` refuses a process that is not serving with `NEEDS_RUNNING_CORE_MSG` (`crates/aitm-sysproxy/src/plugin.rs:28-29,162-164`), while `proxy.system.unset` is documented "works one-shot (§D10)" (`:189`). (2026-11-01)

**F13. The registry is not the same in every process.** 73 verbs are native and always present (the installed 0.5.10 prints exactly 73 in its usage dump with `AITM_NO_BUNDLED_SCRIPTS=1`, run in an isolated `HOME`). The 15 `check.*` verbs and `l4.recon`/`l4.tcp_probe`/`l4.udp_probe` are `ScriptCommand`s registered by bundled Rhai `load(reg)` hooks (`scripts/bundled/active/check-*.rhai`, `scripts/bundled/l4/*.rhai`; `crates/aitm-plugin-rhai/src/command.rs`, default `Sensitive`), and 22 native `l4.*` verbs exist only when `l4.enabled`. `docs/research/mcp-tool-catalog.txt` (113 verbs, #216) lists all of them. A schema-only registry (W2's `describe_commands`, spec D15) would not contain the script verbs unless it loads scripts; the core's `tools/list` is the authoritative list for the core you are talking to. (2026-11-01)

**F14. Four gates, plus one by design, treat `Frontend::Operator` as *not* the CLI.** The bus gives a token-holder exactly two roles, `Mcp` and `Operator` (F2); there is no wire role for `Cli`. Most gates use `caller_is_trusted_control()` (Cli **and** Operator pass): `scope.add` (`crates/aitm-plugins/src/scope.rs:93`), `ca.install` outside system scope (`crates/aitm-ca/src/commands.rs:939`), script authoring (`crates/aitm-plugin-rhai/src/commands.rs:268-276`), `poc.run` (`crates/aitm-poc/src/runner.rs:1107`), `proxy.system.set/unset` (`plugin.rs:65-70`), `agent.*`. But these compare `host.frontend() != Frontend::Cli`:

| Gate | Verbs | Source | Operator over the bus |
|---|---|---|---|
| passthrough list mutation | `tls passthrough add`, `remove` | `crates/aitm-plugin-passthrough/src/lib.rs:102-114` | refused unless `tls.allow_agent_passthrough` |
| map authoring | `map add`, `remove` | `crates/aitm-plugin-maprules/src/lib.rs:442-451` | refused unless `maps.allow_agent_authoring` |
| host-path file I/O | `session save`, `session load`, `flow export`/`import` with `path` | `crates/aitm-plugin-sessionio/src/lib.rs:137-146` | refused unless `session_io.allow_agent_file_io` |
| `script validate` path | `script validate --path` outside `poc.dir` | `crates/aitm-plugin-rhai/src/commands.rs:285-305` | confined to `poc.dir` |
| `ca install` / `ca uninstall` with `--scope system` (by design; `ca` stays local, F16) | | `crates/aitm-ca/src/commands.rs:818-822` | refused: "system scope needs a terminal" |

The rhai file says so in a comment: "This deliberately exempts `Frontend::Operator`, unlike the map-rules gate, which exempts only `Cli`" (`commands.rs:263-266`), and `crates/aitm-core/src/ctx.rs:90-91` calls the Cli-only form legitimate because it fails closed. Consequence: a one-shot that forwards over the bus as operator **regresses** these verbs relative to today's in-process `Frontend::Cli`, and the refusal text blames "an agent frontend". The same gates would bind any operator-token client (TUI, web UI, mac app); I did not check whether those surfaces expose the affected verbs. (2026-11-01)

**F15. The one-shot builds the whole proxy before it dispatches.** In `run()` a `Mode::Cli` process goes `reading config` (`main.rs:428-453`) → `apply_bus_endpoint_file` (`:457`) → `loading detections` (`:525`) → `preparing CA`, which mints or loads the CA (`:602-603`) → `tui::services(&proxy, &cfg, None, …)` and `Cli::new(…).dispatch(argv)` (`:653-690`). The dispatcher's host is `Frontend::Cli`, with no browser (`with_services(…, None)`). `Cli::dispatch` is synchronous and its flag parser takes `ParamSchema` from a local `Registry` (`crates/aitm-cli/src/dispatch.rs:127-170`, `resolve` `:198`). So a discovery step has a natural slot **after `env::apply` / `apply_bus_endpoint_file` (`main.rs:453-457`) and before `loading detections` (`:525`)**, where config is known and nothing has been minted or loaded. (2026-11-01)

**F16. Classification by group.** Evidence is the code path of each group's `invoke`, the 0.5.10 usage text, and the repo's own earlier prose (`site/docs.html:184`: "Use the one-shot form for commands that stand alone: ca, config get, request send, poc run, findings list, script validate"). **L** = acts on live state inside the core (a one-shot's copy is thrown away: false success); **D** = reads or writes only disk or the OS, honest in-process; **?** = ambiguous.

| Group (verbs in 0.5.10) | Tiers seen | What `invoke` touches | Class | Note |
|---|---|---|---|---|
| `agent` (4) | R, S | `AgentState`, audit ring, parked `Ask` requests (per server) | **L** | `agent approve` resolves a request parked on the *core's* server |
| `browser` (7) | R, W, S | the embedded browser handle; the one-shot passes `None` | **L** | `screenshot` returns `Bytes` |
| `ca` (4) | R, S | CA files under `ca.dir`, OS trust store | **D** | `install`/`uninstall` act on the machine, not the core; `--scope system` is CLI-only by design (F14); the `[y/N]` stays local (F20) |
| `capture` (1) | R | live macOS capture feeder status | **L** | one-shot always says "feeder off" |
| `check` (15, script) | default S | host fns over the live store/client/guard | **L** | only present when scripts load |
| `config` (1) | R | the config *this process* holds (redacted) | **?** | one-shot answers for its own config; only the bus answers for the core's (e.g. the embedded core's temp config) |
| `findings` (4) | R, W, S | `findings.dir` on disk, read at invoke time | **D** | `record --finding_capture <flow-id>` names a flow in a store; treat as **?** when it does |

| `map` (3) | default S | live map rules | **L** | `add`/`remove` Cli-only gate |
| `poc` (5) | W, R, default S | `build` reads a flow from the store; `run` uses live egress/guard and writes artifacts; `list`/`get`/`artifact` read `poc.dir` | **L** build, **?** run, **D** list/get/artifact | `run --poc_path` is resolved on the *core's* filesystem if forwarded |
| `proxy` (6) | R, default S, S | `status`/`pause`/`resume` live proxy flags; `system status` OS read; `system set` already refuses a non-serving process; `system unset` works one-shot | **L** status/pause/resume/set; **D** `system unset`; **?** `system status` | `status` in a one-shot reports `listening:false` |

| `scope` (3) | R, S, default S | the live `ScopeRateGuard` | **L** | the R14 case |
| `script` (7) | R, S | `validate`: static compile; `list`/`findings`: live script host; `enable`/`disable`/`reload`: live host; `save`: disk write **and** live hot-swap | **D** validate; **L** the rest | `save` alone on disk would be a silent half-success |
| `session` (2) | default S | live store ↔ disk | **L** | `save` from a one-shot writes an *empty* session file; Cli-only gate |
| `tls` (3) | default S | live `PassthroughList` | **L** | `add`/`remove` Cli-only gate |
| `ws` (3) | default S | live WS conversations | **L** | |

**Candidate rule, fail-closed like `Sensitivity`'s default:** a verb is **live** unless it is named **local**; unclassified verbs, including script-registered ones, are live. On the evidence the local set is `ca *`, `findings *` (with the `record` caveat), `poc list|get|artifact`, `script validate`, `proxy system unset`, `scan report`, and, under a stated rule, `config get` / `proxy system status` (see §4.3). (2026-11-01)

### 3.4 What "no running core" looks like today (brief item 4)

**F17. Words already in the tree for a dead or absent bus:**
- the sole existing one-shot refusal: `proxy.system.set needs a running core: use the app, the TUI or the web UI, or start aitm with `system_proxy.auto: true`` (`crates/aitm-sysproxy/src/plugin.rs:28-29`; it spells a dotted name, which W2 bans in prose);
- the port-in-use panel (spec M2) already says an `aitm` holder is "most likely held by another running `aitm`, the aitmproxy macOS app's embedded core, or another program";
- bus client: `connecting to the bus at 127.0.0.1:60680` + the OS error (`aitm-bus-client/src/lib.rs:160`), `bus connection closed: …`, `bus connection refused the token` (`aitm-bus-client/src/lib.rs:200,246-247`);
- TUI: `bus down · retrying`; mac: `offline` / "Start the core" / "Reconnect" (F9);
- W1 error panel shape (spec D6, `crates/aitm-term`): `what` (headline, lowercase start), `why` (sentences), `fix` (prose), `command` (own line, `▸` on a TTY, `fix:` piped), `log`; `ErrorKind::Failure` is exit 1, `Usage` is exit 2. Glossary: "core", never "daemon" or "server". (2026-11-01)

### 3.5 Failure modes a one-shot must handle (brief item 5)

**F18. Stale endpoint file** (core died without `Drop`; the mac app leaves its dir after an app crash). Loopback `connect` to a dead port fails at once with `ECONNREFUSED`: classify as "no running core" and name the file. Worse: a **recycled port**. The one-shot writes `{"token":"<operator token>"}` as its first bytes (F8), so a stale file or a fixed `port:` whose core is gone sends the operator token to whatever now listens there. The existing clients share this exposure (TUI `--bus`, the mac app's external lane); the new part is that a *discovery* step makes it implicit. No pre-auth handshake exists in the protocol. (2026-11-01)

**F19. Endpoint present, token wrong.** The server answers one `-32001 unauthorized` and closes (`transport.rs:415-421`); the client surfaces `BusError::Rpc{-32001}` on the first request. Causes on the evidence: the config was edited or `operator-token generate --force` rotated the token after the core started (the confirmation text itself says restart, `operator_token.rs:194-198`), or the one-shot was pointed at a different core's config (`--config`, `AITM_CONFIG`), or the app relaunched (new tokens, new dir). Connected-but-agent is a distinct case: a config without `mcp.operator_token` gives `initialize.role == "agent"`, where `scope.add` is gated ("Refused from an agent frontend (MCP) unless scope.allow_agent_widen is set", the verb's own description, `scope.rs:78-80`). A one-shot must check `role == "operator"` before a state-changing verb. `aitm operator-token generate` is the existing fix command, and needs an existing config. (2026-11-01)

**F20. Confirmations.** `Cli::dispatch` puts `Command::confirm_prompt` to a `Confirmer` unless `--yes` (`dispatch.rs:156-168`, `confirm.rs`); the prompt text is `<prompt> [y/N] ` on stderr and, off a TTY, a refusal that points at `--yes`. Commands with a prompt: `ca.install`/`ca.uninstall` (`aitm-ca/src/commands.rs:1044-1056`) and the confirm-gated `l4.*` verbs (`l4.scope.add`, `l4.inject`, `l4.send_recv`, `l4.intercept.forward`, `l4.intercept.drop`; `confirm_prompt` impls in `crates/aitm-proto-l4/src/commands/{scope,inject,sendrecv,intercept}.rs`). Over the bus an **operator** connection gets the D4 handshake instead: the first call returns `{status:"needs_confirmation", prompt, confirm_token}` (non-error), and the **same connection** must re-send the identical arguments plus `_confirm:"<token>"`; tokens are single-use, bound to connection, command and arguments, and expire (`server.rs:646-661,733-745,1836-1866`; `_confirm` is stripped before the fingerprint, `:1701-1713`). So a remote one-shot can still ask its local `Confirmer` and then re-send; `--yes` still needs the two round trips. `ca.*` stays out of this question if it stays local (F16). (2026-11-01)

**F21. A core on the stdio transport is a third case, not "no core".** Bare `aitm` with the default config serves MCP on stdin/stdout; it publishes no endpoint and listens on no port, so a one-shot cannot tell it from "nothing running" by dialing. The one-shot *can* tell when it reads **the same config** the core read: `mcp.transport` is stdio (or absent, the default), so it can say that a second client is impossible by configuration. For the mac embedded core this never applies (its config is always loopback). Consequence for W1: the ready card's `Scope` row prints `aitm scope add --host <host>` for bare `aitm` and `aitm web` with an empty Scope, whatever the transport (`crates/aitm/src/startup/card.rs:30,191-201,286`; `aitm tui` prints no card), but for a default-config terminal core that command still cannot reach it after R14. (2026-11-01)

**F22. Two cores.** The mac app (proxy `8080` if free, else an ephemeral port; memory `aitmproxy-mac-embedded-core-bus-connect` item 3) and a terminal core can run side by side, as can several embedded cores (F4). Nothing in the config or file formats says which one a one-shot means. Config-derived discovery (`--config`, `AITM_CONFIG`, default) finds the terminal core; the embedded core is reachable only by an explicit pointer. "Newest wins" is already a documented trap. (2026-11-01)

**F23. The one-shot's own `--config`** names which core's config to read for the endpoint and tokens, as it does everywhere else (`main.rs:260-292`, leading `--config`, `AITM_CONFIG`). It is the natural way to say "the core started with this config". It also decides the one-shot's *local* verbs (CA dir, `poc.dir`, `findings.dir`), which can silently differ from the running core's when the core was started with a different config (F5). (2026-11-01)

**F24. Other things the remote path changes.** (a) Paths are resolved by the *core*: `--path out.har`, `--poc_path x.yaml`, `script validate --path` are relative to the core's working directory, not the one-shot's. (b) Calls are recorded by the **core's** audit ring and durable log as origin `operator` with the declared `clientInfo.name`, so a remote one-shot finally leaves the audit line the mac session looked for, and `README.md:303-306` ("No `cli` line is written today, because one-shot CLI commands run in their own process and build no writer") and `README.md:356-358` stop being the whole story for forwarded verbs. (c) Startup cost drops: a forwarded verb needs no CA load, no script load and no assembly. (d) `Windows` is out of scope (spec Non-goals). (2026-11-01)

## 4. Candidate directions for the Architect

These are options with trade-offs, not decisions. The evidence points at **C for terminal cores** and at **one extra published pointer for the embedded core** (D or E); the verb rule and the panel text follow.

### 4.1 Discovery

**A. Endpoint file + config token.** The one-shot resolves an endpoint file (flag, or `mcp.transport.loopback_tcp.endpoint_file` from the config it loaded), reads `host:port` (loopback only, empty/partial = "starting", retry briefly), and takes `mcp.operator_token` from the same config.
- Fits ephemeral ports (`port: 0`) and the embedded core's own artifacts; a missing or unreadable file is a cheap "no core" signal; the token never rides in the file (F1).
- Does not find the embedded core by default (F6); `--bus-endpoint-file` would invert its meaning, so a new flag name is needed (F2); stale after SIGKILL (F18); non-atomic write.

**B. Config port + token only** (what the mac app's external lane does, F5). Dial `127.0.0.1:<loopback_tcp.port>` with `mcp.operator_token`.
- Zero new artifacts; matches INSTALL.md's documented external-core setup (`port: 9090`); works for a terminal core with a fixed port.
- Cannot work for `port: 0` (the embedded core and any ephemeral core); the transport `token` is the *agent* token, so `operator_token` must be present or the verb is gated (F19); an unrelated listener on a fixed port receives the token (F18).

**C. Both, with precedence** (candidate order): explicit `--bus host:port` plus `--token-file`/`AITM_BUS`/`AITM_BUS_TOKEN` (the TUI's flags and env, verbatim, F9) → the loaded config's `endpoint_file` if it exists → the loaded config's non-zero `loopback_tcp.port` → none found. Token from `mcp.operator_token` of the same config (or the explicit token). Config chosen by `--config` → `AITM_CONFIG` → default (F23).
- Covers terminal cores however they were configured and keeps the TUI's contract; stays quiet for the embedded core only if a pointer exists (D/E).
- More code and more words in the refusal (which source was tried).

**D. A published pointer written by every serving core** (Tailscale `ipnport`, Proxyman `mcp-handshake.json`): a fixed, per-user, `0600` file in the aitmproxy dir (name chosen by the Architect) holding the bus address and where the operator token lives. Written on bind, removed in `Drop`.
- The only option that makes `aitm scope add` work with **no flags and no config** for a default terminal core, *if* the core also serves a bus by default, which today it does not (F3): that is a posture change from "operator access off by default" (`config.rs:341-345`) and Matt's call.
- Lifecycle problems: stale file after SIGKILL, two cores overwriting one file (embedded + terminal), `Drop` ordering. Touches `aitm-mcp` or `main.rs` (the file the L4 session is also editing).

**E. App-side pointer for the embedded core only**: the app creates, at each launch, a stable owner-only pointer in the aitmproxy dir to its live per-launch dir (a symlink like Tailscale's `ipnport`, or a small file naming the dir), replaced atomically and removed at stop.
- Keeps tokens in the temp dir (today's "never persisted" posture, F4); fixes "which of the three dirs" (F4, F22); app-only change (Swift) plus a documented contract for the CLI; a dev bundle or sibling session could overwrite the pointer unless it uses an isolated data dir.

### 4.2 Roles

The bus gives only `Operator` and `Mcp` (F14). Options: (i) leave the four Cli-only gates and make the one-shot refuse those verbs remotely with the gate's own text; (ii) change the gates to `caller_is_trusted_control()` like `scope.add` (a core change that also fixes the TUI, web and mac; the rhai file shows the difference was a choice, not an accident); (iii) keep those verbs local-only, which for `tls`/`map`/`session`/`flow export` reintroduces the false success. (i) is honest and cheap; (ii) is the real fix but widens what an operator-token client may do.

### 4.3 Verb rule

- **Default live** (needs a core; unknown and script verbs included), **named local** set per F16, enforced by a test that walks the registry and fails on an unclassified verb (the repo already does this for tiers: `crates/aitm/tests/m4_sensitivity.rs`).
- Where the table lives: a per-command declaration with a fail-closed default (like `sensitivity()`; touches every plugin crate; Rhai `ScriptCommand` defaults live) versus one static table in `aitm`/`aitm-cli` (one file, can drift, mitigated by the walking test).
- Ambiguous verbs need a stated rule: `config get` and `proxy system status` could be "ask the core if one is reachable, else answer locally and say whose config this is", or always live; `poc run` and `findings record` are live when they reference flow ids.
- Remote needs the verb list and flag types: either the local registry (W2's schema-only registry lacks script verbs, F13) or the core's `tools/list` JSON Schema, which `aitm_cli`'s `TypeDesc` parser does not read today.

### 4.4 The refusal (candidate wording, W1 panel shape; exit 1, `ErrorKind::Failure`)

Headline (the orchestrator's decided content, in spec voice, no dotted names):

```text
✕ no running core at 127.0.0.1:9090
  Nothing is listening there, so `aitm scope add` has nothing to change; it will
  not edit a throwaway copy. Nothing was changed.
  Start aitm, or use the app's Scope page.

  ▸ aitm

  Log           ~/Library/Application Support/aitmproxy/logs/aitm.log
```

Piped form: `error: no running core at 127.0.0.1:9090` / `  Nothing is listening there… Nothing was changed.` / `  Start aitm, or use the app's Scope page.` / `  fix: aitm`. **Caveat: `aitm` is a true fix only if the core it starts is discoverable** (default config: stdio, no bus, F3/F21), so either D lands, or the `command` line should be `aitm` with a config that has `mcp.transport.loopback_tcp`, or the fix is the prose sentence alone.

Variants, one per failure mode (the `what` line carries the discriminating fact):
- *Nothing found to dial* (no config transport, no pointer): `no running core found` / why: `Looked for mcp.transport.loopback_tcp in <config> and for the app's embedded core; neither is serving a bus.`
- *Stale endpoint*: `no running core at 127.0.0.1:60680` / why: `The endpoint file <path> names an address nothing is listening on; the core that wrote it has exited.`
- *Config says stdio*: `this config serves MCP over stdio, which a second client cannot reach` / fix: `Set mcp.transport.loopback_tcp and mcp.operator_token in <config> and restart aitm, or run aitm tui.`
- *Token refused*: `the core at 127.0.0.1:9090 refused the operator token in <config>` / why: `The config changed after that core started; a rotated token only takes effect on restart.` / fix: `Restart the core, or pass --config for the core you mean.`
- *Connected as agent*: `the core at 127.0.0.1:9090 would treat this as an agent` / fix: `aitm operator-token generate` then restart.
- *Cli-only verb* (F14, option i): the gate's own sentence, plus `Use the app or the TUI for this, or set <gate> in <config>.`
- *Core did not answer in time*: `a core at 127.0.0.1:9090 accepted the connection but did not answer within 5 s` (deadline value is the Architect's).

**One sentence for the panel:** "No running core at `<endpoint>`, so nothing was changed; start aitm, or use the app's Scope page."

## 5. Open questions

1. **Which discovery for the embedded core?** E (app pointer) or D (core pointer) or an explicit `--bus`/`--config` only. Needs a decision from Matt/Architect because it touches the app, possibly `aitm-mcp`, and `main.rs`.
2. **Should a default terminal core serve an operator bus?** Without it `aitm scope add` can never reach a default `aitm`/`aitm web`/`aitm tui` (F3, F21), and the wave-1 ready card advice stays false for them. Posture change; Matt's call. Related: should the card hide or vary the `Scope` next step by transport?
3. **Operator vs Cli gates (F14).** Fix the four gates, or refuse. Not verified: whether the TUI/web/mac surfaces already hit this for `tls passthrough`, `map`, `session`, `flow export`.
4. **Liveness of the other two embedded-core dirs** on this Mac. Not verifiable here: the sandbox denies loopback `connect` and `ps`/`pgrep` (`sysmond service not found`). A real-shell run of `nc -z` against each `bus.endpoint` address would settle it (read the address files only).
5. **Config mode.** `write_atomically` likely resets a `0600` default config to the umask mode (F7, from code, not run). Does the one-shot refuse or warn on a group/world-readable token-bearing config?
6. **Token to a recycled port (F18).** Is a pre-auth identity check needed (for example a different first line, or a pid/uid check), or is parity with the TUI and mac clients acceptable?
7. **Deadlines.** `aitm-bus-client` has none (F8); the right connect and per-call budgets (a `poc run` or `scan` can take minutes) are unmeasured.
8. **Schema source for remote parsing** (local registry vs the core's `tools/list`, F13/§4.3) and whether `--json` output must be byte-identical between local and remote paths for scripts.
9. **What the published v0.5.9 GitHub body says.** Only the local notes file was read (no network); the premise "0.5.10 recommends `aitm scope add --host <host>`" was not reproduced in any shipped text (F25).
10. **Exit code for "no core".** Every prior-art tool uses `1` for this; gh reserves `4` for auth. Project convention today is `0/1/2`. Whether scripts need to tell "no core" from other failures is unanswered.

11. **Mac-side follow-up (orchestrator, 2026-11-01).** The per-launch dir of F4/F6 is also why the app's fixture self-test picked a *stale* embedded core earlier today (card task_6b977012): with three `aitm-embedded-core/<UUID>/` dirs on disk, nothing says which one is live. The pointer file of direction D would close that trap too if the app's `EmbeddedCore` read it (liveness by connect, not by directory age) instead of its own newest-dir rule. That is a Swift change for the mac lane, not this PR; the spec should list it as a follow-up and keep the pointer's content a contract the app can rely on.

## 7. Method and limits

- I read code; ran the installed 0.5.10 `aitm` once with an isolated `HOME` to list its verbs (and this branch's debug binary once the same way: it prints the W1 panel, not the verb list); and listed metadata (names, modes, sizes) of the embedded-core work dirs. I did **not** read any `config.yaml` there or print or store any token. I attempted bare TCP connects (`nc -z`, one `curl`) to the three `bus.endpoint` addresses and to `127.0.0.1:8080`, sending no token; the sandbox refused every loopback connect (`Operation not permitted`), so no core was reached.
- By mistake I ran `aitm --version` (0.5.10) once against the real `HOME` before switching to an isolated one. In 0.5.10 that boots the one-shot path (research 24, R11) and loads the existing CA; a listing afterwards showed no file in `~/Library/Application Support/aitmproxy/` newer than the app's own audit writes at 17:07, so nothing was created or changed.
- Per-command sensitivity tiers come from a script that reads every `impl Command` block in `crates/*/src` (names plus `fn sensitivity`); `COMPLEX` bodies in `aitm-proto-l4` and `aitm-ca` were resolved by reading them. The group table summarises tiers, it does not list all 100-plus verbs.
- Unverified, marked in the text: liveness of the other two work dirs (open question 4); the file mode `operator-token generate` leaves (F7, code only); the published v0.5.9 release body (open question 9); the Proxyman and Tailscale behaviour comes from their docs and source as fetched, not from running them.
