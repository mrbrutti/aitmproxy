The PoC format

A PoC is a saved, re-runnable reproduction of a finding: a few steps and one success condition, in a YAML file a colleague can read top to bottom. Write one when you confirm something; run it again when you need to know whether it is still true.

What a PoC is

Findings decay. A screenshot proves what was true on Tuesday; a PoC proves what is true now. aitmproxy stores a PoC as a declarative file rather than a script so that it has no hidden state, can be diffed and reviewed like code, and can be written by a person first and an assistant second. A script step is there for the cases that need real logic. The requests a PoC sends go through the proxy's own client, so the flows it generates are captured and inspectable like any other traffic.

You can also start from traffic you have already captured. poc.build turns a flow into a parameterized PoC and returns it as YAML text; it writes no file. The base URL becomes {{target}}, and credential headers (Cookie, Authorization, Proxy-Authorization, X-Api-Key) become required variables, so no secret lands in a file you share.

Schema

The file must be .yaml or .yml and at most 1 MiB, and YAML anchors and aliases (&a, *a) are rejected. Unknown top-level keys are ignored, but id, info, steps and success must be present.

KeyTypeMeaning
idstring, requiredA slug: lowercase letters, digits and hyphens, at most 64 characters, starting with a letter or digit. It names the run's output directory and file, and is the finding's poc_ref.
info.namestring, requiredOne line a reader understands without opening anything else. It becomes the finding's title.
info.severityinfo | low | medium | high | critical, requiredCarried onto the finding when the PoC passes.
info.cwestringOptional, such as CWE-79. It is the finding's class; without it the first tag is, then the id.
info.description, info.author, info.reference, info.tags, info.metadatastring, string, list, list, mapOptional, and kept as written when a file is saved and reloaded.
variableslistOptional. Each entry is a map with name and, optionally, default, description and required; see Variables.
stepslist, requiredRun in order. Each entry is a map with one key naming the step type.
successrequiredA matcher, a list of matchers (all must hold), or all, any or not over matchers. Evaluated after the last step. The PoC passes if and only if it is true.

Step types

httpsend one request through the proxy
method and url are required; url is absolute and templated, usually {{target}}/path. Optional headers (a map), body (a string) and extract (a list of extractors, below). The request goes through the proxy's guarded client, so the host must be in scope and rate limits apply. The response is what later success matchers and extractors read, and its flow is the finding's capture. A step's own matchers and matchers-condition are kept when a file is saved but not evaluated; put the checks in success.
browserdrive the embedded browser
action is one of navigate (url), click (target, a CSS selector), type (selector, text), eval (expr; the value is kept for browser-eval matchers and extractors) or screenshot (label). It needs the embedded browser, and a run without one fails. navigate is scope- and SSRF-guarded. Only the last screenshot is kept.
extractbind a variable from the last response
name and type, which is regex (regex, and group, where the default 0 is the whole match), json (json, a dotted path such as data.token), kval (kval, a response header name) or browser-eval (expr, a value an earlier eval step kept). The value is available as {{name}} to later steps and to dsl matchers. An extractor that finds nothing binds nothing. The same entries work as a list under an http step.
scripta Rhai escape hatch
script is Rhai source that may return pass or return fail; it can read and set run variables with vars.get(name) and vars.set(name, value). An optional name lets success read the verdict as step("name"), which is "pass", "fail", "neutral" or "error". It runs in the scripting sandbox, behind the same guards as everything else.
l4and other protocol steps
Any other step key names a protocol, run by that protocol's handler; one nobody registered fails at run time, never silently. l4 takes op (craft, inject or send_recv) and can bind a field of the received packet, such as field: tcp.flags. It runs only where the L4 module is enabled: a privileged core, Linux first.

Matchers and success

Matchers live in success. They are judged against the most recent http response, plus anything an extractor, a script step or a browser step bound.

typefieldstrue when
statusstatus (one integer)the response status equals it
wordword (a string), partthe part contains the string
regexregex, partthe pattern matches the part
dsldsl (an expression)the expression is true
browser-evalexpr, equalsthe value expr gives in the page equals equals

part is body (the default), header or all. Any matcher takes negative: true to invert it. Combine matchers with all, any and not; a bare list means all, and an empty one is rejected. A dsl matcher may stand alone as - dsl: 'status_code == 200'. Patterns and expressions are checked before the first request goes out, so a bad regex fails the run early. Editor completion also lists size and binary matchers; the engine does not run them yet and rejects them as unknown.

A dsl expression reads status_code, body, content_length and any variable an extractor, a script step or a protocol step bound, and combines them with ==, !=, &&, ||, ! and parentheses. Its functions are contains, url_encode, base64, html_escape, to_lower, len, concat, rand_text_alpha and step. Variables from variables reach an expression as {{name}}, by text substitution before it is evaluated.

Variables

Anything in {{double braces}} is substituted before a step runs, and again inside success. A placeholder is one of three things:

  • a variable name, such as {{param}};
  • one of the runtime placeholders computed from the target variable: {{BaseURL}} and {{RootURL}} (the scheme and authority), {{Hostname}}, {{Host}} (the hostname with its port, if the target gave one), {{Port}} (80 or 443 when it gave none), {{Path}} and {{Scheme}};
  • a DSL expression, such as {{url_encode(payload)}}.

No names are reserved. target is the one the command line fills (--target), so a PoC file never hard-codes a host. A value supplied at run time beats a default, and a variable with neither is an error the first time something uses it. required: true marks a variable the caller is expected to supply; the engine does not check it on its own.

A default may itself be a placeholder. Defaults are evaluated once at the start of the run, in order, so a later one can use an earlier one. That is how a PoC gets a fresh marker each run: marker below is a random string, and payload wraps it, so a reflection cannot be a coincidence or a cache. Data from a response reaches later steps only through an extractor.

Complete example

A reflected value in a search parameter, from the project's own test fixture. The first step sends a payload that carries a random marker. The second and third drive the embedded browser to the same URL and keep a screenshot. success asks for three things at once: the page answered 200, the marker came back in the body unescaped, and the page's own JavaScript set window.__aitm to the marker, which is a stronger claim than text in a body. Against a patched target that escapes the quote, the word check fails and so does the PoC.

Running a PoC

poc.run loads the file, runs the steps in order with no agent in the loop, judges success and writes its artifacts. http steps go through the proxy's guarded client, so the target must be in scope (scope.entries in config.yaml); browser steps also need the embedded browser. --target fills the variable target, and --vars takes a JSON object of any others; both beat a default. The path must end in .yaml or .yml, and when poc.dir is set, poc.run, poc.get and poc.list are confined to that directory.

cli$ aitm poc run --poc_path pocs/status-check.yaml --target https://staging.example.com --vars '{"param":"q"}'
agentpoc.run({ poc_path: "pocs/reflected-xss-search-q.yaml", target: "https://staging.example.com", vars: { param: "q" } })

The one-shot CLI has no browser attached, so it runs only PoCs without browser steps or browser-eval matchers. That is why the first line names a different file: the example above needs the browser, so run it by agent or from a UI's Findings panel (Run again). Either way the result has the same shape, and the CLI prints it as JSON:

passed is the verdict, and evaluated lists each leaf of success with whether it matched. A PoC that runs and fails still returns normally, so the CLI exits 0 whether passed is true or false, and exits 1 only when the command itself errors: a bad file, an out-of-scope host, a missing browser. To use a PoC as a regression test in CI, test the field, for example aitm poc run … | jq -e .passed.

The three artifacts

  • Finding capture (finding_capture): the flow of the last http step, as an id in the flow store. With no http step the newest flow captured during the run stands in, and a run that captured nothing fails. The one-shot CLI's store ends with the command, so the id matters most in a long-lived core.
  • The PoC file (poc_path): a YAML copy, <id>.poc.yaml, in a fresh owner-only directory aitm-poc-<id>-… under poc.out_dir, or the system temp directory when that is unset.
  • The screenshot (screenshot_path): screenshot.png in the same directory when the PoC took one, and an empty string when it did not. poc.artifact reads either file back, confined to poc.out_dir.

Where findings go

A passing run also records a finding when findings.dir is set: <findings.dir>/<id>.yaml plus a line in runs.jsonl, and its id comes back as recorded_id. The title is info.name, the class is info.cwe (else the first tag, else the PoC id), the severity is info.severity and the target is the target variable; the record points at the PoC file, the screenshot and the capture. With no findings.dir, nothing is persisted. findings.record writes the same kind of record by hand, for something you confirmed manually, and findings.list and findings.get read them back.

By agent: over MCP, poc.run is refused unless poc.allow_agent_run is true. Operator sessions and the one-shot CLI are never gated: the terminal UI and the macOS app's own core are operator sessions, and the web UI becomes one when mcp.operator_token is set. poc.run is also a write command, so the agent policy applies: it runs under auto, all and ask and is refused under readonly and paused. Scope, rate limits and the SSRF check apply in every case. Calls an assistant makes are recorded in the audit ring with their origin, and agent.activity reads it.

aitmproxy

A fast, memory-safe intercepting proxy for inspecting and editing HTTP, WebSocket and HTTP/2 traffic, and raw L4 on a privileged Linux core, during development and authorized testing. Use it on systems you own or are permitted to test.
