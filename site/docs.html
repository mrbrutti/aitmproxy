Getting started

Ten minutes from an empty terminal to a request held in mid-air and edited, first by you in a UI, then by an assistant. The same commands sit behind the macOS app, the web UI, the terminal UI and the MCP server.

Install

aitmproxy ships for macOS and Linux; Windows is not supported. The aitm command is the core: it runs the proxy, serves the web UI (aitm web), the terminal UI (aitm tui) and the MCP server, and runs one-shot commands. The embedded browser is a separate engine that aitm finds beside itself; the macOS app, the Linux packages and the release tarballs bundle it. Pick the path for your OS — the download page lists every package and checksum for v0.5.4.

Showing

macOS (Apple Silicon)

Install from the project's public Homebrew tap — no account or token needed. The formula and the app are Apple Silicon only, and the app needs macOS 26 or later. The app bundles its own core, so it does not need the formula.

Linux (x86-64 and aarch64)

Download the package for your distribution and CPU from the download page (the .deb comes as amd64 or arm64, the .rpm as x86_64 or aarch64), then install it. It places aitm and aitm-tui on your PATH (installed under /usr/lib/aitmproxy, symlinked from /usr/bin), with the embedded browser alongside. The file names below follow the current release and your CPU.

Cargo, or from source

The source repository is private, so this needs git credentials with access to it, and Rust 1.97 or newer. A bare build produces only aitm: no aitm-tui, no browser engine, and no built web UI (aitm web serves a placeholder until the web app is built). Prefer the packages above unless you are developing.

Trust the certificate

To read HTTPS, aitmproxy terminates TLS with a certificate authority it generates on your machine, for your machine. The CA key stays there; ca export writes the certificate only. Before browsers and apps will accept it, that CA must be trusted. The embedded browser already trusts it and needs no install.

The ca commands print their result as JSON (shortened above). ca install and ca uninstall ask before they touch a trust store; without a terminal, pass --yes to confirm, and --dry_run lists what would run and changes nothing. On macOS the default scope is the login keychain, and ca status reports whether the certificate is present, not whether its trust settings are right, so confirm Always Trust in Keychain Access. Linux has no per-user store: its scope is system, which writes to the system ca-certificates anchors and so needs the privileges for that.

By agent: an assistant connected over MCP can call ca.status() and ca.export() any time, and ca.install({ dry_run: true }) to preview. A real ca.install or ca.uninstall is refused under the default agent policy, and even under the all policy unless you also set ca.allow_agent_install: true in config.yaml. Trust decisions stay with the person at the keyboard.

For a device that is not this machine (a phone, a VM), export the certificate with aitm ca export --out aitm-ca.pem (it refuses to overwrite an existing file) and install it there by the device's usual means. Hosts that pin their certificates can be excluded with TLS passthrough.

Capture

Run the proxy with a UI. aitm web listens for traffic on 127.0.0.1:8080 and serves the web UI on 127.0.0.1:8082. It prints a one-time link carrying the web UI's token; you open it yourself, because nothing is opened for you. aitm tui runs the same proxy with the terminal UI in one process. Point a browser, a simulator or your app at the proxy and flows start arriving.

The --cacert file is the PEM from aitm ca export --out aitm-ca.pem; leave it off if the client already uses the trust store you installed the CA into. Capture is passive and needs no scope. Scope gates the active tools (replay, request.send, the browser, the scanner, PoC runs), and the UIs refuse to act on a held flow whose host is not in scope. Intercept and edit

Interception parks a request before it leaves the proxy: readable and editable, going nowhere until you resume or kill it. You do it from a UI, because the web UI, the terminal UI and the macOS app are attached to the running proxy.

  1. Open a UI: the link aitm web printed, aitm tui, or the macOS app.
  2. Press I to arm interception. The web UI shows a bar reading Intercept armed — every request pauses here. Armed with no rules, every new request is held at the request phase; responses are not.
  3. Trigger the traffic from your app. Held requests show as paused, counted in the bar. Select one.
  4. Press E (e in the terminal UI) and edit the held request: its headers, the raw request or the body. Nothing is sent yet. In the web UI the edit bar counts your pending edits, and Apply alone changes the held request without releasing it.
  5. Release it with Apply & Resume (⌘↩), which sends your edit and then lets the request go. In the terminal UI press Ctrl-S or F5 inside the editor. Or kill it (⌘\, or d in the terminal UI); the web UI's Kill menu offers Reset connection, Respond 429 Too Many Requests and Respond 503 Service Unavailable.

A UI will not edit, replay or kill a flow whose host is out of scope; it says Out of scope — add <host> to scope to act. Add the host to scope first, from the Scope panel or scope.entries in config.yaml.

The CLI is one-shot. aitm <family> <verb> builds its own empty core, runs one command and exits. It does not connect to a proxy you started with aitm, aitm web or aitm tui, so aitm flow list, aitm flow mutate and aitm flow resume cannot see or release that proxy's held flows. Use the one-shot form for commands that stand alone: ca, config get, request send, poc run, findings list, script validate. scan discover is not on that list: it needs the running core's embedded browser, which a one-shot process does not have.

To hold only some traffic, interception takes rules: a method, a host, a URL pattern and a phase (request, response, ws_frame or any). An assistant sets them with flow.intercept, below; the web UI's Rules… button is disabled for now. A rule with phase response parks the response on its way back, and an edit to a parked response may also set status.

The same thing, by agent

An assistant connected over MCP calls the same commands under the same names. Arming interception is a sensitive command, so under the default auto policy an assistant cannot do it: you arm it with I, or set the policy to ask, which holds the call until you approve it in a UI. Connect an assistant (MCP)

aitmproxy is an MCP server: every registered command is exposed to an assistant under the same name and shape. Connect one and it drives the proxy — hold, edit, replay, script, reproduce — through the same core you use by hand. Running aitm with no arguments starts the proxy and the MCP server together. The transport is one of stdio (the default), loopback TCP or streamable HTTP, and aitm serves exactly the one you configure. How you connect depends on whether the client launches a command or reaches a URL.

Start aitm and the endpoint is http://127.0.0.1:8084/mcp. Every request must carry Authorization: Bearer <token>, or it is refused with 401. path defaults to /mcp; allowed_origins defaults to empty, which accepts no cross-origin request. There is no TLS in the listener, and it exposes the proxy's control plane, so keep it on loopback and put a tunnel or HTTPS in front of it before anything else reaches it. Keep the token secret: whoever holds it can drive the proxy as an agent.

Loopback TCP

The third transport is a plain newline-delimited JSON-RPC socket on 127.0.0.1. It is what the macOS app uses to attach to an external core:

The first line of every connection must be {"token":"…"} with exactly that one key, or the connection is refused with error -32001.

Least privilege: an assistant connects as an agent under the auto policy. Read and write commands run; sensitive ones are refused even if their own switch is on. To allow one, you set the policy to all and open its gate in config.yaml (ca.allow_agent_install for the CA, scope.allow_agent_widen for scope), or set ask and approve each call in a UI. poc.run is a write command but has its own switch, poc.allow_agent_run, off by default. Every call is recorded with its origin in the audit ring (agent.activity).

aitmproxy

A fast, memory-safe intercepting proxy for inspecting and editing HTTP, WebSocket and HTTP/2 traffic, and raw L4 on a privileged Linux core, during development and authorized testing. Use it on systems you own or are permitted to test.
